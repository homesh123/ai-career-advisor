🚦 Shipping prompt changes safely: versioning, evals in CI and gradual rollout

EnglishHinglish

🏠 Real-life example

A sweet shop testing a new laddoo recipe doesn't replace every box on Diwali morning. It writes the recipe down with a version number, has the staff taste it against the old one, sells it in one branch first, and keeps the old recipe ready in case customers complain. Prompts deserve the same care, because a one line prompt change can change every answer your product gives.

💡 In simple words

Treat prompts, model names and settings (temperature, tools, retrieval settings) as code. Keep them in version control or a prompt registry with a version ID, and log that ID with every request so you can tell which version produced an answer. Before merging a change, run your eval set automatically in CI: the golden questions, format checks, safety tests and LLM-as-judge scores, compared against the current version, with a rule such as "no metric drops by more than 2 points". Look at the failures, not just the average. Then release gradually: put the new version behind a feature flag, send 5% of traffic to it (a canary), watch online signals such as thumbs down, edits, escalations, latency and cost, then increase. If something goes wrong, roll back by switching the flag, without a redeploy. Upgrading the model itself is the same kind of change: run evals first, because a newer model can still behave differently on your tasks. Keep a short changelog explaining why each version changed.

🎬 See how it works

A new prompt version must pass the eval gate in CI, then goes to 5% of users behind a flag. If online signals stay healthy it grows to 25% and 100%; if not, one switch rolls it back.

🪜 Step by step

  1. Move prompts out of scattered strings into versioned files or a prompt registry, each with an ID like support@v14.
  2. Log the prompt version and model with every request so any answer can be traced back.
  3. Add an eval job to CI that compares the candidate with the current version and fails the pull request on agreed regressions.
  4. Review a sample of changed answers side by side, not only the scores.
  5. Release behind a feature flag to 5% of traffic, watch online signals for a day or two, then increase in steps.
  6. Keep rollback to one switch, and write a changelog entry for each version.

🔑 Key terms

Prompt registry
A versioned store of prompts and model settings that the app loads by ID.
Eval gate in CI
An automatic check that blocks a change if eval scores drop below the agreed rule.
Canary release
Sending a small share of traffic to the new version first and watching it.
Feature flag
A switch that turns a version on or off for some users without a redeploy.

👀 See it in action

yaml
# .github/workflows/prompt-evals.yml
on: pull_request
jobs:
  evals:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm ci
      - run: npm run evals -- --candidate prompts/support@v14 --baseline prompts/support@v13
      # fails the PR if: faithfulness drops > 2 pts, format errors > 0, safety tests fail

# After merge: flags.support_prompt = { v14: 5%, v13: 95% }
# Watch thumbs-down rate, escalations, p95 latency, cost/request for 48 h → 25% → 100%
# Problem? set v14: 0% (instant rollback, no redeploy)

Version the prompt, gate it on evals in CI, release to 5% behind a flag, then roll forward or back.

⚠️ Common mistakes to avoid

  • Editing the prompt directly in production on a Friday evening because "it's only text".
  • Upgrading to a newer model without running evals, assuming newer always means better for your task.
  • An eval set that never grows, so new failure types from production keep slipping through.

✅ Quick check

A teammate improved the support prompt and it reads better. What should happen before all users get it?

  1. Run the eval set against the current version in CI, then release to a small share of traffic behind a flag
  2. Ship it to everyone because it reads better
  3. Ask the model whether the new prompt is better
Show answer

A. Run the eval set against the current version in CI, then release to a small share of traffic behind a flag: A prompt that reads better can still break formats or cases you rely on. Evals catch regressions before release, and a canary limits the damage of anything they miss.

🙋 Questions learners ask

How big should the CI eval set be?

Start with 50 to 200 cases covering common, hard and risky inputs, and add every real failure you fix. Keep it fast enough to run on every pull request.

Can LLM-as-judge scores be trusted in CI?

Partly. Check the judge against human labels first, use clear rubrics, and combine it with exact checks (format, required facts) that don't need a judge.

🎯 Asked in interviews on this topic

Try answering out loud first, then open the model answer.

How do you ship a change to a prompt, or upgrade the model, without breaking things for users?

💬

I treat prompts and model settings as code. They live in version control or a prompt registry with a version ID, and every request logs which version answered. A pull request that changes a prompt runs our eval set in CI against the current version: golden questions, format checks and safety tests, with a rule like no metric may drop more than two points. I also read a sample of answers that changed. After merge, the new version goes behind a feature flag to about 5% of traffic while we watch thumbs down, edits, escalations, latency and cost, then we increase in steps. Rollback is one switch. A model upgrade goes through exactly the same process.

✅

  • Prompts versioned and logged per request
  • Eval gate in CI against the current version
  • Read changed answers, not only scores
  • Canary behind a feature flag, watch online signals
  • One switch rollback; model upgrades follow the same path

: Whether you can iterate fast without regressions.

📌 Remember

Version prompts like code, gate changes on evals in CI, release to a small share first, and keep one-switch rollback.
