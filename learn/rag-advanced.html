🔎 Production RAG: chunking, hybrid search, reranking and debugging

EnglishHinglish

🏠 Real-life example

Searching a medical textbook by 'meaning' alone is great when someone asks 'how to treat high fever', but terrible when a doctor searches an exact medicine code like 'PCM-650mg'. And if a table of dosages was sliced in half across two pages, neither half makes sense. Production RAG fixes both: it splits documents along real headings and tables (smart chunking), searches by both meaning and exact words (hybrid search), and uses a careful second reader (reranker) to pick the best 5 passages.

💡 In simple words

Basic RAG demos break in production for three reasons: bad chunking, missed exact terms, and noisy top-k results. First, split by document sections, headings and tables (~300–600 tokens with 10–15% overlap) and attach metadata (title, section, date, permissions) to every chunk. Second, use hybrid search: combine dense vector search (for meaning) with BM25 keyword search (for IDs, product codes and names) using Reciprocal Rank Fusion. Third, fetch the top 30–50 chunks quickly, then pass them through a cross-encoder reranker to keep the best 5. Finally, measure retrieval (Recall@k, MRR) separately from generation (faithfulness, answer relevance) so you always know which half to fix.

🎬 See how it works

Hybrid search combines exact keyword matches (BM25) with meaning matches (vectors), then a reranker scores the top candidates to hand only the best 5 chunks to the LLM.

🪜 Step by step

  1. Parse documents with structure intact: keep section headings with their paragraphs, and keep tables together as Markdown or HTML rather than slicing mid-row.
  2. Attach rich metadata to every chunk: document_id, title, section_path, updated_at, and allowed_roles for permission filtering.
  3. Run hybrid retrieval: combine BM25 lexical search (exact keywords, SKUs, names) and vector search (semantic meaning) using Reciprocal Rank Fusion (RRF).
  4. Pass the top 30–50 retrieved chunks to a cross-encoder reranker (e.g. BGE-Reranker or Cohere Rerank) and send only the top 5–8 to the LLM.
  5. Evaluate retrieval and generation separately on a 50-question golden set: track Recall@5 and MRR for retrieval, and faithfulness/groundedness for the answer.

🔑 Key terms

Hybrid search (BM25 + vectors)
Combining keyword search (for exact terms and codes) with embedding search (for meaning).
Cross-encoder reranker
A second-stage model that reads the query and each candidate chunk together to score exact relevance.
Recall@k vs Faithfulness
Recall@k checks if the right chunk was retrieved in the top k; faithfulness checks if the LLM stuck to those chunks without making things up.

Filter permissions first, retrieve broadly with hybrid search, rerank tightly, then generate with citations.

⚠️ Common mistakes to avoid

  • Debugging a wrong RAG answer by tweaking the system prompt before checking whether the right document chunk was even retrieved!
  • Dumping 30 chunks into the LLM prompt ('lost in the middle'): latency and cost jump while answer accuracy drops compared with 5 reranked chunks.

  2. Increase LLM temperature to 1.0
  3. Delete all error codes from the docs

A. Add BM25 keyword search alongside vector search (hybrid search) plus a reranker: Dense embeddings compress meaning and often blur exact alphanumeric codes; BM25 matches exact tokens while vectors match meaning.

🙋 Questions learners ask

Why not just put every document into a 1-million-token context window instead of RAG?

Passing 500,000 tokens on every user query costs dollars per question and takes 15–30 seconds to first token. RAG retrieves the relevant 2,000 tokens in 50 ms at 1/200th the cost.

What is query rewriting or HyDE in RAG?

Users type short or messy follow-up questions ('what about for contractors?'). A fast LLM step rewrites the follow-up into a standalone search query using chat history before searching the index.

🎯 Asked in interviews on this topic

Try answering out loud first, then open the model answer.

Users say your RAG bot gives a wrong answer, even though the right document exists. How do you debug it?

💬

I'd find out where the chain broke, step by step. One: was the document indexed at all? Check ingestion logs. Two: was it retrieved? Run the query and see if the right chunk is in the top results; if not, it's a retrieval problem, like bad chunking, a filter excluding it, or the query wording differing from the document's wording. Three: was it retrieved but cut off, because of the context limit? Four: was it in the prompt, but the model ignored or misread it? That's a prompt or model problem. I'd add this case to an evaluation set and measure retrieval and generation separately, so I can fix the right part and prevent it coming back.

✅

  • Classify the failure: not indexed, not retrieved, ranked too low, truncated, or misused by the model
  • Inspect each stage with logs and traces
  • Fixes depend on stage: chunking, hybrid search, reranking, prompt changes
  • Add the case to an eval set; measure retrieval and generation separately

: Structured debugging. The step by step classification is what top answers do.

How do you choose a chunking strategy for RAG?

💬

Chunks should be big enough to hold a complete idea, but small enough to be precise. I start by respecting the document's structure: split by headings, sections or paragraphs instead of every fixed number of characters, so a table or a step list isn't cut in half. A typical starting size is a few hundred tokens with a small overlap. I attach metadata like title, section and date to each chunk, which helps filtering and citations. Then I test different sizes against an evaluation set of real questions, and keep whatever gives the best retrieval recall.

✅

  • Structure aware splitting (headings, paragraphs, tables)
  • Starting size plus overlap; tune by evals
  • Metadata on each chunk
  • Measure with retrieval recall on real questions

What are hybrid search and reranking, and why do they help?

💬

Vector search is good at meaning but can miss exact terms like product codes, names or error numbers. Keyword search, like BM25, is great at exact terms but misses paraphrases. Hybrid search runs both and merges the results, so you get the best of each. Reranking is a second step: take the top 50 or so candidates and let a more accurate, slower model, a cross encoder, score each one against the question, then keep the best 5. Together they usually give a big jump in retrieval quality for little extra effort.

✅

  • Vector = meaning; keyword = exact terms
  • Hybrid merges both result lists
  • Reranker rescores a shortlist more accurately
  • Trade off: a bit more latency for much better precision

How do you evaluate and improve a production RAG pipeline on complex PDFs and tables?

💬

I separate retrieval metrics from generation metrics. For retrieval, I track Recall@k and MRR on a golden question-to-source-chunk dataset; for generation, I measure faithfulness (zero unsupported claims) and answer relevance. Complex PDFs usually fail because naive character chunking slices tables and loses section headers. I fix that with layout-aware parsing that keeps tables intact as Markdown, prepends the document title and section breadcrumb to every chunk before embedding, combines BM25 + dense vectors with Reciprocal Rank Fusion, and uses a cross-encoder reranker to pick the top 5 chunks.

✅

  • Evaluate retrieval (Recall@k, MRR) separately from generation faithfulness
  • Layout-aware parsing that keeps Markdown tables intact and prepends section headers
  • Hybrid search (BM25 + dense embeddings) merged with Reciprocal Rank Fusion (RRF)
  • Cross-encoder reranking + query rewriting for multi-turn chats

: Tests whether you have built RAG beyond a 20-line tutorial.

Design a chatbot that answers employee questions from 50,000 internal documents.

💬

Clarify first: who are the users, which document types, how often they change, required latency, and who can see what. Ingestion: connectors to each source, text extraction, structure aware chunking, embeddings, and a vector store with metadata and permissions. Query: rewrite the question if it's part of a conversation, hybrid search filtered by the user's permissions, rerank, and send the top chunks to the LLM with instructions to cite and say when it doesn't know. Quality: an eval set of real employee questions, measuring retrieval recall and answer faithfulness. Operations: logging, feedback buttons, cost and latency monitoring, and incremental re indexing when documents change.

✅

  • Clarifying questions first
  • Ingestion: connectors, chunking, embeddings, metadata, permissions
  • Query: rewrite, hybrid search, permission filter, rerank, grounded generation with citations
  • Evals, feedback, monitoring, index freshness

: The most common LLM system design question.

📌 Remember

Chunk by structure, retrieve with BM25 + vectors, rerank top 50 → top 5, and measure retrieval vs generation separately.
