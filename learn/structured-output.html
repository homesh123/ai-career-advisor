🧾 Structured outputs: JSON schemas, validation and retries

EnglishHinglish

🏠 Real-life example

When you fill a bank form, there are fixed boxes: name, PAN, amount. The clerk can type it straight into the system because every answer is in its box. If you wrote a free letter instead, someone would have to read and retype it. Structured output asks the model to fill the form, not write a letter, so your code can use the answer directly.

💡 In simple words

Most AI product features are not chat: they extract fields from an email, classify a ticket, fill a form or return data for a UI component. For these, you want JSON that matches a schema. Define the schema once in code (Zod in TypeScript, Pydantic in Python) and use it three ways: send it to the model (structured output or tool calling mode, which most providers support), validate the response, and type your code. Even with schema mode, validate: values can be in the wrong range, dates can be invented and enums can drift. On a validation failure, retry once with the error message added ("total must be a number"), then fall back to a safe default or human review. Keep schemas small and flat, give every field a description, allow null for "not found" so the model doesn't invent values, and add an enum for categories. Check business rules in plain code afterwards: totals add up, dates are not in the future, IDs exist in your database.

🎬 See how it works

The model fills a schema instead of writing free text. Your code validates it: valid data is saved, an invalid answer gets one retry with the error, and anything still wrong goes to a person.

🪜 Step by step

  1. Write the schema first (Zod or Pydantic) with a description on every field, enums for categories and nullable fields for values that may be missing.
  2. Use the provider's structured output or tool calling mode and pass the schema, instead of asking for JSON in plain words.
  3. Validate every response against the same schema; on failure, retry once with the validation error in the prompt.
  4. Check business rules in plain code: totals add up, IDs exist, dates make sense. Route anything that fails to human review.
  5. Build an eval set of 50 or more real inputs with expected fields and measure accuracy per field, not just "valid JSON".

🔑 Key terms

JSON schema
A description of the exact fields, types and allowed values the output must have.
Zod / Pydantic
Libraries that define a schema once and validate data against it in TypeScript or Python.
Validate and retry
Check the output; if it fails, ask again with the error, then fall back.
Nullable field
A field that may be null, so the model can say "not found" instead of guessing.

👀 See it in action

typescript
import { z } from "zod";
import { generateObject } from "ai";

const Ticket = z.object({
  category: z.enum(["billing", "delivery", "technical", "other"]),
  orderId: z.string().regex(/^A\d{5}$/).nullable().describe("null if not mentioned"),
  urgency: z.number().int().min(1).max(5),
  summary: z.string().max(200),
});

const { object } = await generateObject({ model, schema: Ticket, prompt: email });
// object is typed and already validated against the schema
if (object.orderId && !(await orderExists(object.orderId))) object.orderId = null; // business rule in code

One schema drives the model, the validation and your types; business rules are still checked in plain code.

⚠️ Common mistakes to avoid

  • Parsing JSON out of a free text answer with a regex. It breaks on the first unusual reply; use schema mode and validation.
  • Making every field required, which pushes the model to invent order numbers, dates and amounts.
  • Huge nested schemas with 60 fields in one call. Split into steps or smaller schemas for better accuracy.

✅ Quick check

An invoice email has no order number. How should your extraction schema handle it?

  1. Make orderId nullable with a description "null if not mentioned"
  2. Ask the model to write "unknown" inside the summary
  3. Make orderId required so the model always fills it
Show answer

A. Make orderId nullable with a description "null if not mentioned": A required field pushes the model to invent a value. Allowing null gives it an honest way to say the data isn't there.

🙋 Questions learners ask

Structured output or tool calling?

Use structured output when you always want one object back. Use tool calling when the model should decide which action to take, each with its own schema.

Can the model still return wrong values in valid JSON?

Yes. Valid shape doesn't mean correct content. That's why you add range checks, business rules and a field level eval set.

🎯 Asked in interviews on this topic

Try answering out loud first, then open the model answer.

How do you get reliable JSON out of an LLM for a feature that fills a form or a database?

💬

I define one schema in code, with Zod or Pydantic, and use it three ways: I pass it to the model through the provider's structured output or tool calling mode, I validate every response against it, and I use it as the type in my code. I keep fields small and described, use enums for categories, and make fields nullable when the value may be missing so the model doesn't invent it. If validation fails I retry once with the error message, then fall back to human review. After that I still check business rules in plain code, like totals adding up and IDs existing, and I measure accuracy per field on a set of real examples.

✅

  • One schema for the model, validation and types
  • Structured output or tool calling mode, not "please reply in JSON"
  • Nullable fields and enums to stop invented values
  • Validate, retry once with the error, then fall back
  • Business rules in code and a field level eval set

How do you write automated tests for code that calls an LLM?

💬

I separate code correctness from answer quality. All model calls go through one function, so in unit tests I replace it with a fake that returns fixed responses, including bad ones such as invalid JSON, an empty answer, a timeout or a 429, and check my parsing, retries and fallbacks. For end to end flows I replay recorded real responses as fixtures, and re-record them when the prompt or model changes. Contract tests check that outputs match the schema and that prompts only contain the current user's data. A small live smoke test runs on a schedule to catch provider changes. Answer quality is judged separately by the eval suite. The pull request suite stays fast, free and deterministic.

✅

  • Fake model for unit tests, including failure cases
  • Recorded responses for end to end flows
  • Contract tests for schemas and data isolation
  • Scheduled live smoke tests
  • Evals for quality, kept separate from tests

: Engineering discipline around non-deterministic systems.

📌 Remember

One schema for prompt, validation and types; allow null, validate, retry once, then fall back.
