🧠 Context engineering and memory: what goes into the prompt, and what to remember

EnglishHinglish

🏠 Real-life example

Before a doctor sees you, the nurse hands over a one page summary: your name, allergies, today's complaint and last visit's notes. The doctor doesn't reread your whole file from birth. Context engineering is preparing that one page for the model on every call: only what it needs right now, in a clear order.

💡 In simple words

A model remembers nothing between calls; your app sends everything again each time. So every request is assembled from parts: the system prompt (role, rules, format), user and account facts (name, plan, language), retrieved documents, tool results, the recent conversation, and the new question. Context engineering is choosing and ordering these parts within a token budget. Long chats grow without limit, so keep the last few turns word for word and replace older turns with a short running summary. Long term memory means saving stable facts the user shares ("I prefer Hindi", "my store is in Pune") in your database, with the user's consent and a way to view and delete them, then adding the relevant ones to future prompts. Keep each user's memory and documents strictly separate: filter by user and tenant in code, never by asking the model. More context is not always better: irrelevant text raises cost and latency and can confuse the answer (lost in the middle). Put stable instructions first (which also helps prompt caching) and the question last.

🎬 See how it works

Every call rebuilds the prompt from parts inside a token budget: rules first, then facts, memories and documents, a summary of old turns, the recent turns, and the question last.

🪜 Step by step

  1. List every context source for your feature: rules, user facts, memories, documents, tool results, recent turns, and the question.
  2. Set a token budget per source (for example rules 800, documents 3,000, history 1,500) and trim the lowest value parts first.
  3. Order it: stable instructions first, then facts and documents, then recent turns, with the question last.
  4. Summarise older turns when the chat passes a limit and keep the summary updated as the chat grows.
  5. Save long term memories only with consent, show users what is remembered, and let them edit or delete it.
  6. Enforce user and tenant filters in every database and vector query, and test that user A can never see user B's data.

🔑 Key terms

Context engineering
Choosing and ordering what goes into each model call within a token budget.
Running summary
A short summary that replaces older chat turns so long chats stay small.
Long term memory
Stable user facts saved in your database and added to future prompts, with consent.
Tenant isolation
Keeping each customer's data separate, enforced by filters in code.

👀 See it in action

python
def build_context(user, chat, question, budget=6000):
    parts = [SYSTEM_PROMPT]                                   # stable rules first (cacheable)
    parts.append(f"User: {user.name}, plan={user.plan}, language={user.lang}")
    parts += [m.text for m in memories.relevant(user.id, question, k=3)]  # filtered by user_id in code
    parts += [d.text for d in search(question, tenant=user.tenant, k=5)]
    older, recent = chat[:-6], chat[-6:]
    if older:
        parts.append("Earlier in this chat: " + summarise(older))  # running summary
    parts += [f"{m.role}: {m.text}" for m in recent]
    parts.append(f"user: {question}")                         # question last
    return trim_to_budget(parts, budget)

Every call is rebuilt: rules, user facts, memories, documents, a summary of old turns, recent turns, then the question.

⚠️ Common mistakes to avoid

  • Sending the full chat history forever. Cost and latency grow with every message and quality drops.
  • Asking the model to "only use this user's documents" instead of filtering in code. A prompt is not an access control.
  • Remembering sensitive details (health, money, passwords) without asking, or without a way to delete them.

✅ Quick check

Your support chat gets slower and more expensive the longer a conversation runs. What's the best fix?

  1. Keep the last few turns as they are and replace older turns with a short running summary
  2. Switch to a model with a bigger context window
  3. Delete the history so every message starts fresh
Show answer

A. Keep the last few turns as they are and replace older turns with a short running summary: A summary keeps what matters from earlier while the prompt stays small, so cost and latency stop growing. Deleting history breaks follow-up questions.

🙋 Questions learners ask

Isn't a 1 million token context window enough to skip all this?

It fits more, but every token still costs money and time, and models use long context less reliably. Choosing the right context is still cheaper and more accurate.

How is memory different from RAG?

RAG retrieves shared knowledge such as help articles. Memory stores facts about one user. Both are added to the prompt, but memory needs consent, editing and strict per-user isolation.
