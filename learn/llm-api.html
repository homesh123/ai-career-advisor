🔌 Calling an LLM API: keys, requests and costs

EnglishHinglish

🏠 Real-life example

Ordering on Zomato: you send a request (what you want and where), the restaurant processes it, and you get a response (the food). You pay per order, and your account login proves who you are. An LLM API works the same way: your code sends a request with messages, the model replies, you're billed per token, and the API key is your login.

💡 In simple words

Providers like Anthropic and OpenAI let you use their models over the internet through an API. You send a list of messages (system and user) plus settings like model name, max tokens and temperature, and get back the generated text. Keep API keys secret: put them in environment variables, never in code or GitHub. Plan for errors and rate limits with retries and timeouts. Streaming sends the answer word by word so users aren't kept waiting. Track cost: input tokens plus output tokens multiplied by the price per token.

🪜 Step by step

  1. Create an API key in the provider's console and store it in an environment variable, never in code.
  2. Send a request with the model name, a system message (instructions) and user messages; read the text from the response.
  3. Log input and output token counts. Cost = tokens × price per token, so you can estimate cost per user.
  4. Handle failures: set a timeout, retry rate limit (429) and server errors with exponential backoff, and show a friendly message if all retries fail.
  5. Stream long answers so users see text immediately, and set a max token limit to control cost.

🔑 Key terms

API key
A secret password that identifies your account to the API.
Rate limit
The maximum number of requests allowed per minute.
Streaming
Receiving the reply piece by piece as it's generated.

👀 See it in action

python
import os, anthropic
client = anthropic.Anthropic(api_key=os.environ["ANTHROPIC_API_KEY"])

msg = client.messages.create(
    model="claude-sonnet-5-5",
    max_tokens=300,
    system="You are a concise travel assistant for Indian travellers.",
    messages=[{"role": "user", "content": "3-day Jaipur plan on a budget?"}],
)
print(msg.content[0].text)
print(msg.usage)   # input/output tokens → cost

The key comes from an environment variable, never pasted into code.

⚠️ Common mistakes to avoid

  • Committing API keys to GitHub. Bots find them within minutes; rotate the key immediately if it happens.
  • Calling the API from browser code, which exposes your key. Call it from your server.
  • No usage limits. A bug or abuse can create a huge bill; set budgets and per user limits.

✅ Quick check

Where should your API key live?

  1. In an environment variable or secret manager
  2. In the README
  3. Hard-coded in app.py
Show answer

A. In an environment variable or secret manager: Keys in code end up on GitHub and get stolen. Use environment variables or a secrets manager.

🙋 Questions learners ask

Which model should I start with?

Start with a strong general model to prove the feature works, then test smaller, cheaper models on your eval set and switch where quality holds.

Is my data used for training?

Policies differ by provider and plan. Business API plans usually don't train on your data by default, but always check the current terms.

🎯 Asked in interviews on this topic

Try answering out loud first, then open the model answer.

What are tokens and the context window, and why do they matter in a product?

💬

Tokens are the chunks of text a model reads and writes; in English, one token is roughly three quarters of a word. The context window is the maximum number of tokens the model can handle at once, including the prompt, any documents, the chat history and the answer. They matter for three reasons: cost, because APIs charge per token; latency, because more tokens take longer; and quality, because if your documents don't fit, you have to choose what to include, which is why we use retrieval.

✅

  • Token ≈ part of a word; pricing and limits are in tokens
  • Context window includes input and output
  • Impacts cost, speed and what information the model can see

How do you safely read files, call an external API and handle rate limits or network errors in Python?

💬

For files, I always use a with open(..., encoding='utf-8') block so the file closes automatically even if an exception happens, and I stream large datasets with JSON Lines (.jsonl) one line at a time. For API calls, I always pass an explicit timeout so a hung server never freezes my worker, check the HTTP status code, and catch specific exceptions like TimeoutError or HTTPError rather than a bare except. When an LLM API returns 429 (rate limit) or 503, I retry a few times with exponential backoff and random jitter so all workers don't retry at the exact same second.

✅

  • Use with context managers for files and .jsonl for large data
  • Always set an explicit timeout on HTTP / LLM API calls
  • Catch specific exceptions, never bare except
  • Retry 429 / 5xx errors with exponential backoff and jitter

: Every AI engineer calls APIs and reads files daily; interviewers look for production habits.

How do you get reliable JSON output from an LLM?

💬

First, use the provider's structured output or JSON mode with a schema, which constrains the model to valid JSON. Second, keep the schema simple, with clear field descriptions and allowed values, and set temperature low. Third, always validate in code, for example with Pydantic: check types, required fields and ranges. If validation fails, retry once with the error message, and if it still fails, fall back safely, like marking the item for manual review, rather than crashing. And I log the failures to improve the prompt.

✅

  • Native structured output or JSON mode with a schema
  • Simple schema, clear descriptions, low temperature
  • Validate with code (e.g. Pydantic)
  • Retry with the error, then a safe fallback

: Production reliability, very common in AI product engineer interviews.

Your LLM feature is too slow and too expensive. What do you do?

💬

First I measure where tokens and time go: prompt size, output size, number of calls. Then the main levers: stream the response so users see text immediately; shorten prompts and retrieved context; cache answers to repeated questions and use prompt caching for long fixed system prompts; route easy requests to a smaller, cheaper model and only hard ones to the big model; reduce agent steps; and batch background jobs. After each change, I rerun evals, so I know quality didn't drop.

✅

  • Measure first: tokens, calls, time per step
  • Streaming for perceived latency
  • Shorter context, caching, smaller models via routing, fewer steps
  • Check quality with evals after each change

: Cost and latency trade offs are a top 2026 theme.

Why do LLM products stream responses, and how would you implement it?

💬

Generating a full answer can take several seconds, but the first words are ready in a fraction of a second. Streaming shows text as it's generated, so the product feels fast even though total time is the same. To implement it, I call the LLM API with streaming on, read the chunks as they arrive on the server, and forward them to the browser with server sent events or a WebSocket, appending them to the UI. I handle a stop button, network errors mid stream, and I only run checks like JSON validation after the stream finishes.

✅

  • Time to first token vs total time
  • Server reads chunks, forwards via SSE or WebSocket
  • UI appends text; supports cancel
  • Validation and logging after completion

: Hands on product engineering.

Design a pipeline that processes 10,000 documents a day with an LLM, for example extracting fields from invoices.

💬

Ingest new documents into object storage and put a job per document on a queue. Workers pull jobs, extract text with OCR if needed, call the LLM with a structured output schema, validate the result in code and write it to a table with the document ID, model version and prompt version. Handle the LLM's rate limits with a controlled number of workers and retries with exponential backoff. Make processing idempotent by document ID, so retries don't duplicate. Send failures and low confidence results to a review queue. Track cost per document against a budget, and sample outputs regularly for an accuracy check.

✅

  • Queue based, idempotent per document
  • Structured output plus validation
  • Rate limit handling: concurrency control, backoff retries
  • Dead letter or review queue; cost and quality monitoring

: A 2026 favourite: classic data engineering plus LLM realities.

How do you get reliable JSON out of an LLM for a feature that fills a form or a database?

💬

I define one schema in code, with Zod or Pydantic, and use it three ways: I pass it to the model through the provider's structured output or tool calling mode, I validate every response against it, and I use it as the type in my code. I keep fields small and described, use enums for categories, and make fields nullable when the value may be missing so the model doesn't invent it. If validation fails I retry once with the error message, then fall back to human review. After that I still check business rules in plain code, like totals adding up and IDs existing, and I measure accuracy per field on a set of real examples.

✅

  • One schema for the model, validation and types
  • Structured output or tool calling mode, not "please reply in JSON"
  • Nullable fields and enums to stop invented values
  • Validate, retry once with the error, then fall back
  • Business rules in code and a field level eval set

Your AI feature's response time doubled since yesterday. How do you investigate?

💬

Check what changed: deploys, prompt changes, a model version change, or a provider status issue. Then look at traces to find which step got slower: retrieval, the LLM call, a tool call or our own code. If it's the LLM call, see whether prompts or outputs got longer, for example a bigger retrieved context or a prompt change that makes answers longer, or whether the provider's latency rose. If it's ours, check database queries, cache hit rate and traffic volume. Fix the cause, roll back if needed, and add a latency alert per step so we catch it sooner next time.

✅

  • What changed? deploys, prompts, models, provider
  • Use per step traces to localise
  • Token count changes are a common cause
  • Fix or roll back; add per step alerts

: Systematic debugging of AI systems.

📌 Remember

Request in → response out, billed per token. Guard the key, and handle errors.
