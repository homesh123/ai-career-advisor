🧪 Evaluating AI: how to know it actually works

EnglishHinglish

🏠 Real-life example

A restaurant doesn't judge a new dish by the chef's opinion alone. They run tasting sessions with a fixed checklist (taste, temperature, presentation) across many plates. Evals are tasting sessions for AI: a fixed set of real questions with clear scoring, run every time you change the prompt or model.

💡 In simple words

LLM outputs vary, so 'it looked good in a demo' isn't evidence. Build an eval set: 30 to a few hundred real inputs with expected answers or grading rules. Score them automatically where you can (exact match, contains the right citation, valid JSON), use an LLM-as-judge with a clear rubric for open-ended quality, and spot-check by hand. Track the score on every change, like unit tests for AI. For agents, measure task success rate, steps and cost. Evals are what separate production AI engineers from demo builders.

🪜 Step by step

  1. Write down what good means for your feature, with examples of good and bad outputs.
  2. Collect 50 to 200 real inputs: common cases, edge cases and past failures.
  3. Choose how to score each: code checks where possible (valid JSON, right category), a rubric for open answers.
  4. Use an LLM judge for the rubric only after checking it agrees with human ratings on a sample.
  5. Run the eval on every prompt or model change, track the score over time, and add every new production failure to the set.

🔑 Key terms

Eval set
A fixed collection of test inputs with expected results.
LLM-as-judge
Using an LLM with a rubric to grade another model's answers.
Regression
Here: a change that makes previously good answers worse.

⚠️ Common mistakes to avoid

  • Testing by trying a few prompts by hand ('vibe checks'). It misses regressions you didn't think to try.
  • An eval set made only of easy examples. Include the tricky and adversarial ones.

  2. Ask the model whether it improved

🙋 Questions learners ask

How many examples do I need?

Start with 50 good ones; that already catches most regressions. Grow towards hundreds per important category over time.

What are online evals?

Signals from real usage after launch: thumbs up or down, edits to AI output, escalations to humans, task completion.

🎯 Asked in interviews on this topic

Try answering out loud first, then open the model answer.

Users say your RAG bot gives a wrong answer, even though the right document exists. How do you debug it?

💬

I'd find out where the chain broke, step by step. One: was the document indexed at all? Check ingestion logs. Two: was it retrieved? Run the query and see if the right chunk is in the top results; if not, it's a retrieval problem, like bad chunking, a filter excluding it, or the query wording differing from the document's wording. Three: was it retrieved but cut off, because of the context limit? Four: was it in the prompt, but the model ignored or misread it? That's a prompt or model problem. I'd add this case to an evaluation set and measure retrieval and generation separately, so I can fix the right part and prevent it coming back.

✅

  • Classify the failure: not indexed, not retrieved, ranked too low, truncated, or misused by the model
  • Inspect each stage with logs and traces
  • Fixes depend on stage: chunking, hybrid search, reranking, prompt changes
  • Add the case to an eval set; measure retrieval and generation separately

: Structured debugging. The step by step classification is what top answers do.

How do you evaluate and improve a production RAG pipeline on complex PDFs and tables?

💬

I separate retrieval metrics from generation metrics. For retrieval, I track Recall@k and MRR on a golden question-to-source-chunk dataset; for generation, I measure faithfulness (zero unsupported claims) and answer relevance. Complex PDFs usually fail because naive character chunking slices tables and loses section headers. I fix that with layout-aware parsing that keeps tables intact as Markdown, prepends the document title and section breadcrumb to every chunk before embedding, combines BM25 + dense vectors with Reciprocal Rank Fusion, and uses a cross-encoder reranker to pick the top 5 chunks.

✅

  • Evaluate retrieval (Recall@k, MRR) separately from generation faithfulness
  • Layout-aware parsing that keeps Markdown tables intact and prepends section headers
  • Hybrid search (BM25 + dense embeddings) merged with Reciprocal Rank Fusion (RRF)
  • Cross-encoder reranking + query rewriting for multi-turn chats

: Tests whether you have built RAG beyond a 20-line tutorial.

How do you reduce hallucinations in an LLM product?

💬

Several layers. Ground the model with RAG and tell it to answer only from the provided sources and to say "I don't know" when they don't contain the answer. Ask for citations, so users and code can check them. Lower the temperature for factual tasks. Validate outputs with code where possible, for example checking that a quoted number actually appears in the source. For high risk cases, route low confidence answers to a human. And measure the hallucination rate with an eval set, so every prompt or model change is checked.

✅

  • Grounding with retrieval and an "I don't know" rule
  • Citations and automated checks
  • Low temperature, structured output
  • Human review for risky cases; track the rate with evals

: Responsible engineering; every LLM role gets this.

How do you evaluate an LLM application?

💬

I start by defining what good looks like for the task, then build an evaluation set of real examples, say 50 to 200 to start, covering common cases, edge cases and known failures. For each, I decide how to score: exact checks with code where possible, like valid JSON or the right category; for open answers, a rubric scored by humans or by an LLM judge that I've checked against human ratings. For RAG I measure retrieval and answer quality separately. I run this suite on every prompt or model change, like unit tests, and I also watch real usage: thumbs down, edits and escalations.

✅

  • Define "good" first, then build a dataset from real cases
  • Code checks where possible; rubric and LLM judge where needed
  • Separate retrieval and generation metrics for RAG
  • Run on every change; add online signals from users

Can you trust an LLM as a judge?

💬

Partly, if you calibrate it. LLM judges have known biases: they favour longer answers, the first option shown, and their own style, and their scores can vary between runs. So I give the judge a clear rubric with examples, ask for a reason before the score, compare its ratings with human ratings on a sample until they agree well, swap the order of options when comparing two answers, and keep the judge model fixed. Wherever the outcome can be checked by code, like a correct calculation or the right database state, I use that instead of a judge.

✅

  • Known biases: length, position, self preference, variance
  • Rubric, reasoning, calibration against humans
  • Prefer executable checks when possible

: Nuance; a frequent follow up to the evals question.

How do you test and evaluate an agent?

💬

At three levels. Unit level: test each tool and the parsing of tool calls with normal code tests. Step level: given a situation, does the agent choose the right tool with the right arguments? I build a dataset of these decisions and score them. End to end: run full tasks in a sandbox with fake or test systems and check the final state, for example "was the right refund created, and nothing else?". I also track the number of steps, cost and time per task, and I test failure cases: tools returning errors, and prompts that try to make it misbehave.

✅

  • Unit tests for tools
  • Step level decision evals
  • End to end tasks in a sandbox, checking final state
  • Track steps, cost, latency; test errors and attacks

: Agent specific evaluation depth.

What's different about operating LLM applications compared with classic ML models?

💬

Several new things to manage. Prompts are code, so they need versioning, review and testing. Evaluation suites must run on every prompt or model change, because there's no single accuracy number. Cost has to be monitored per request and per feature, since it scales with tokens. Providers update models, so I pin versions and re run evals before upgrading. Logging and tracing every step of a chain or agent is essential for debugging. And there are safety checks: prompt injection, PII in logs, and content filters.

✅

  • Prompt versioning and testing
  • Eval suites as release gates
  • Token cost monitoring
  • Model version pinning, tracing, safety controls

Your AI demo fails in front of the customer. What do you do?

💬

Stay calm and be honest: "That's a wrong answer, so let me show you why it happened." Then use it: open the trace, show which document was retrieved and where it went wrong, and explain how we'd catch this with our evaluation set and fix it. Customers trust people who understand their system's failures more than people who pretend there are none. Afterwards, I'd add the case to the eval set, fix it, and follow up with the result. And next time, I'd rehearse with their real data and have a recorded backup.

✅

  • Stay calm, acknowledge it
  • Turn it into a demonstration of control: trace, explain, fix plan
  • Follow up with the fix
  • Prevention: rehearse with real data, backup recording

: Composure and honesty under pressure.

How would you define success metrics for an AI feature?

💬

In layers, so no single number hides problems. Model quality: accuracy, hallucination rate or rubric scores on an eval set. User outcome: did it help? Task completion, time saved, how much users edit the AI's output. Adoption and engagement: how many eligible users try it and come back. Business: revenue, cost per ticket or retention. Plus guardrail metrics that must not get worse, like complaints, latency and cost per use. A very accurate feature nobody uses is still a failure, and a popular one with a high error rate is a risk.

✅

  • Layers: model quality, user outcome, adoption, business
  • Guardrails: errors, latency, cost, complaints
  • Leading vs lagging metrics
  • No single metric stands alone

: The most common AI PM analytical question.

How do you know your AI feature is good enough to launch?

💬

Before building, I define "good" with the team: a set of real examples with expected outputs and a scoring rubric, often 100 or more per important category, taken from real tickets or documents. We set launch thresholds, for example 90% correct on common cases and zero critical errors on safety cases, and compare against the current baseline, often humans. Then we run a limited beta with real users, track the layered metrics, and launch more widely once both offline evals and real usage meet the bar. After launch, evals keep running on every change.

✅

  • Define good before building: eval set and rubric
  • Launch thresholds, including zero tolerance categories
  • Compare to the current baseline
  • Beta with real users, then wider launch; evals continue

How would you build a chatbot that answers students' questions from college notices and PDFs?

💬

I'd use RAG. First, collect the notices and PDFs, extract their text, split it into chunks of a few paragraphs, create embeddings and store them in a vector database. When a student asks a question, embed the question, find the most similar chunks, and send them to an LLM with the instruction to answer only from them and to show which notice the answer came from. If nothing relevant is found, it should say so and point to the office. I'd test it with 30 real student questions, fix the failures, deploy it with Streamlit, and add a feedback button.

✅

  • RAG: ingest, chunk, embed, store
  • Retrieve and answer with citations
  • "I don't know" when there's no answer
  • Test set, deployment, feedback

Design a chatbot that answers employee questions from 50,000 internal documents.

💬

Clarify first: who are the users, which document types, how often they change, required latency, and who can see what. Ingestion: connectors to each source, text extraction, structure aware chunking, embeddings, and a vector store with metadata and permissions. Query: rewrite the question if it's part of a conversation, hybrid search filtered by the user's permissions, rerank, and send the top chunks to the LLM with instructions to cite and say when it doesn't know. Quality: an eval set of real employee questions, measuring retrieval recall and answer faithfulness. Operations: logging, feedback buttons, cost and latency monitoring, and incremental re indexing when documents change.

✅

  • Clarifying questions first
  • Ingestion: connectors, chunking, embeddings, metadata, permissions
  • Query: rewrite, hybrid search, permission filter, rerank, grounded generation with citations
  • Evals, feedback, monitoring, index freshness

We launched an AI tutor. Under 10% of users love it, most find it useless. What do you do?

💬

First, understand the split. Who are the 10%: which grades, subjects or use cases? And what does "useless" mean for the rest: wrong answers, too generic, too slow, or just not what they needed? I'd read real conversations, look at where users drop off, and talk to both groups. If the 10% share a clear use case, like exam revision in maths, I'd double down there: improve quality for that case with evals, and change onboarding so new users start with it. For the rest, fix the top failure reasons or stop showing the feature to segments where it doesn't fit.

✅

  • Segment the lovers vs the rest
  • Diagnose with conversations, funnels, interviews
  • Double down on the use case that works
  • Fix top failures or narrow the audience

Your AI feature costs too much per user. Walk me through how you would reduce cost without hurting quality.

💬

First I measure: cost per request and per active user by feature, model and prompt version, so I know where the money goes. Then I work through the levers in order of risk. I route simple steps, like classification or query rewriting, to a smaller model and keep the switch only if my evals stay within an agreed limit. I make the long system prompt prefix identical across calls and turn on prompt caching. I add a response cache for repeated questions, with the user or tenant in the cache key so nobody sees someone else's answer. I cut tokens with shorter instructions, fewer chunks after reranking and a max output length. Anything not needed right away moves to batch processing. I report the before and after cost together with the quality scores.

✅

  • Measure cost by feature, model and version first
  • Route easy steps to small models, checked by evals
  • Prompt caching with a stable prefix
  • Response cache with identity in the key
  • Fewer tokens and batch where possible; show before and after with quality

: Cost awareness, one of the most common production questions in 2026.

How do you ship a change to a prompt, or upgrade the model, without breaking things for users?

💬

I treat prompts and model settings as code. They live in version control or a prompt registry with a version ID, and every request logs which version answered. A pull request that changes a prompt runs our eval set in CI against the current version: golden questions, format checks and safety tests, with a rule like no metric may drop more than two points. I also read a sample of answers that changed. After merge, the new version goes behind a feature flag to about 5% of traffic while we watch thumbs down, edits, escalations, latency and cost, then we increase in steps. Rollback is one switch. A model upgrade goes through exactly the same process.

✅

  • Prompts versioned and logged per request
  • Eval gate in CI against the current version
  • Read changed answers, not only scores
  • Canary behind a feature flag, watch online signals
  • One switch rollback; model upgrades follow the same path

Design an AI "summarise this thread" feature for a team chat app.

💬

Clarify: thread length, languages, latency target and privacy rules. Flow: when the user clicks summarise, the backend fetches the messages they can see, trims or chunks very long threads, and calls the LLM with a prompt asking for decisions, open questions and action items with owners, in a structured format. Stream the result into the UI with a "draft" label and links to the source messages. Cache summaries and update them incrementally when new messages arrive. Evaluate with a set of real threads, scored for missed decisions and invented facts. Track usage, thumbs down and cost per summary.

✅

  • Clarify constraints
  • Permission aware fetching, chunking long threads
  • Structured prompt; streaming UI with source links
  • Caching, evals, metrics
