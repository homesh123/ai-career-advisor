🔥 PyTorch in practice: tensors, autograd and the training loop

EnglishHinglish

🏠 Real-life example

Practising free throws in basketball has a fixed five-step rhythm: clear your head from the last shot, take the shot, see how far you missed the hoop, feel which way to adjust your wrist, and make that small adjustment. A PyTorch training step follows the exact same five lines: zero_grad, forward pass, loss, backward, step.

💡 In simple words

PyTorch is the standard deep learning framework in both research and production. Data lives in Tensors (NumPy-like arrays that run on GPUs with .to('cuda')). When a tensor has requires_grad=True, PyTorch's autograd engine records every operation and computes all derivatives automatically when you call loss.backward(). Inside each batch of the training loop you must call optimizer.zero_grad() first (because PyTorch adds gradients up by default), run the model, compute the loss, call loss.backward(), and call optimizer.step(). During evaluation, switch to model.eval() and wrap predictions in 'with torch.no_grad():' to save memory and disable dropout.

🪜 Step by step

  1. Wrap your dataset in a torch.utils.data.Dataset and DataLoader(batch_size=32, shuffle=True) so batches stream efficiently.
  2. Move model and batches to the same device: device = 'cuda' if torch.cuda.is_available() else 'cpu'.
  3. In each training step: optimizer.zero_grad() → out = model(x) → loss = criterion(out, y) → loss.backward() → torch.nn.utils.clip_grad_norm_(model.parameters(), 1.0) → optimizer.step().
  4. Use torch.amp.autocast('cuda', dtype=torch.bfloat16) for mixed-precision training: it cuts GPU memory nearly in half and speeds up tensor cores.
  5. After each epoch, switch to model.eval() and 'with torch.no_grad():' to compute validation loss and save the best checkpoint.

🔑 Key terms

Autograd
PyTorch's automatic differentiation engine that computes gradients during loss.backward().
zero_grad()
Clears old gradients from the previous batch so they don't add onto the new batch.
DDP / FSDP (ZeRO)
Distributed Data Parallel copies the model across GPUs; FSDP shards weights, gradients and optimiser states across GPUs to fit huge models.

👀 See it in action

python
model.train()
for x, y in train_loader:
    optimizer.zero_grad()          # 1. clear old gradients
    preds = model(x)               # 2. forward pass
    loss = loss_fn(preds, y)       # 3. measure error
    loss.backward()                # 4. compute gradients
    optimizer.step()               # 5. update weights

model.eval()
with torch.no_grad():
    val_preds = model(val_x)

The 5-line PyTorch training loop, followed by memory-safe evaluation.

⚠️ Common mistakes to avoid

  • Forgetting model.eval() during validation or inference: Dropout keeps dropping neurons randomly and BatchNorm uses batch stats instead of learned running stats!
  • Storing loss tensors in a Python list for logging ('losses.append(loss)' instead of 'losses.append(loss.item())'), which keeps the entire computation graph in GPU memory and causes CUDA Out-Of-Memory!

✅ Quick check

What happens if you forget 'optimizer.zero_grad()' inside a PyTorch training loop?

  1. PyTorch refuses to run
  2. Gradients from every batch accumulate on top of each other, corrupting the weight updates
  3. The model automatically switches to CPU
Show answer

B. Gradients from every batch accumulate on top of each other, corrupting the weight updates: PyTorch accumulates gradients into .grad by design (useful for gradient accumulation), so you must clear them before each step.

🙋 Questions learners ask

What is the difference between DataParallel (DP) and DistributedDataParallel (DDP)?

Always use DDP, never DP. DP uses a single Python process and suffers from GIL contention and uneven GPU memory; DDP runs one process per GPU and synchronises gradients with fast all-reduce.

When do I need FSDP or DeepSpeed ZeRO instead of DDP?

When a single GPU cannot hold a full copy of the model, gradients and Adam optimizer states. FSDP (ZeRO Stage 3) shards all three across GPUs and gathers layers on the fly.

🎯 Asked in interviews on this topic

Try answering out loud first, then open the model answer.

Walk through a PyTorch training loop and explain why optimizer.zero_grad(), model.eval() and torch.no_grad() matter.

💬

Inside each batch of a PyTorch epoch there are five steps: move inputs and targets to the device, call optimizer.zero_grad() because PyTorch accumulates gradients by default, run the forward pass logits = model(x), compute the loss, call loss.backward() to compute gradients via autograd, and call optimizer.step() to update weights. During validation or inference I call model.eval() so Dropout is turned off and BatchNorm uses running statistics, and I wrap the forward pass in with torch.no_grad(): so PyTorch doesn't build the computation graph, cutting memory use roughly in half. For large models I add bf16 mixed precision, gradient clipping, and Distributed Data Parallel (DDP) or FSDP.

✅

  • 5-step loop: zero_grad → forward → loss → backward → step
  • Why zero_grad matters: gradients accumulate across batches by default
  • model.eval() + torch.no_grad() for validation and inference
  • Production training: bf16 mixed precision, grad clipping, DDP vs FSDP
