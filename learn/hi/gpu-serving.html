⚡ LLMs ko efficiently serve karna: GPUs, batching aur cost

EnglishHinglish

🏠 Asli zindagi ki misaal

Ek baar mein ek passenger le jaane wala auto slow aur per person mehenga padta hai. Bus thode second rukkar bharti hai aur utne hi fuel mein kahin zyaada log le jaati hai. LLM servers isi wajah se ek GPU pe bahut saari user requests ko 'batch' karte hain: kahin behtar throughput, aur har request ki cost kam.

💡 Aasaan shabdon mein

Open models (Llama, Qwen, Mistral) khud host karne ke liye GPUs chahiye, aur GPUs mehenge hain. vLLM ya TGI jaise inference servers continuous batching (chalti requests ke beech nayi requests jodna) aur conversation cache ke liye efficient memory se GPU ka poora use karte hain. Key metrics: time to first token (jawaab kitni jaldi shuru hota hai), tokens per second, p95 latency aur har 1,000 requests ki cost. Quantisation models ko chhota karke saste GPUs mein fit karta hai, repeat prompts ki caching paise bachaati hai, aur saamne laga LLM gateway traffic route karta hai, budgets lagaata hai aur providers ke beech fallback karta hai.

🪜 Step by step

  1. Woh sabse chhota model chuno jo aapke eval set pe quality bar paar kare.
  2. Saste GPUs pe fit karne ke liye quantisation (8 bit ya 4 bit) socho, quality thodi hi girti hai; naap ke dekho.
  3. Continuous batching aur efficient KV cache memory ke liye LLM inference engine (vLLM, TGI) se serve karo.
  4. Realistic load pe time to first token, tokens per second aur 1,000 requests ka cost naapo.
  5. Queue length pe autoscale karo, repeat prompts cache karo, aur aasaan requests chhote models pe bhejo.

  • GPUs ko sirf per hour price se compare karna. Apne asli traffic pe per request cost compare karo.
  • Default mein self hosting. Kam volume pe API aksar sasti aur bahut simple hoti hai.

Jawaab dekho

B. Continuous batching wala inference server: Batching same GPU pe zyaada requests daalta hai, jisse utilisation aur throughput badhte hain.

🙋 Seekhne wale yeh poochhte hain

Batching kya hai aur kyun madad karti hai?

Bahut saari requests ek saath process karne se GPU busy rehta hai. Continuous batching intezaar karne ke bajaye naye requests chalte batch mein jod deti hai.

LLM kab self host karein?

Jab data aapke environment se bahar na ja sake, jab volume itna ho ki sasta pade, ya jab fine tuned open model chahiye.

🎯 Is topic pe interviews mein poochhe jaane wale sawaal

Pehle khud bolkar jawaab dene ki koshish karo, phir model answer kholo.

Aapka LLM feature bahut slow aur mehenga hai. Kya karoge?

💬

Pehle naapta hoon tokens aur time kahan ja rahe hain: prompt size, output size, calls ki ginti. Phir main levers: response stream karo taaki user ko turant text dikhe; prompts aur retrieved context chhote karo; repeat sawaalon ke jawaab cache karo aur lambe fixed system prompts ke liye prompt caching; aasaan requests chhote, saste model pe aur sirf mushkil wali bade model pe bhejo; agent steps kam karo; aur background jobs batch karo. Har change ke baad evals dobara chalao, taaki quality na gire.

✅

  • Pehle naapo: tokens, calls, har step ka time
  • Feel hone wali speed ke liye streaming
  • Chhota context, caching, routing se chhote models, kam steps
  • Har change ke baad evals se quality check

: Cost aur latency ke trade offs 2026 ka bada topic hain.

Self attention ka computational cost kya hai, aur ise kaise kam karte hain?

💬

n tokens aur dimension d ke sequence mein attention har token ko har doosre se compare karta hai, to time lagbhag O(n² · d) aur attention matrix ko O(n²) memory chahiye. Isliye lambe contexts mehenge hain. Kam karne ke tarike: FlashAttention, jo exact attention tiles mein nikaal ke memory bachata hai aur GPUs pe kaafi tez hai; sparse ya sliding window attention, jo sirf paas ke tokens dekhta hai; linear attention approximations; aur inference mein KV cache plus grouped query attention, jo per token memory kam karte hain.

✅

  • Sequence length mein O(n²)
  • FlashAttention: exact, memory efficient, IO aware
  • Sparse ya windowed attention, linear approximations
  • Inference tricks: KV cache, GQA

: Efficiency ki gehraai, jo labs ke liye zaroori hai.

LLM inference mein KV cache kya hai?

💬

LLM ek ek token generate karta hai, aur har naye token ko pichhle saare tokens pe attention chahiye. Cache ke bina har step pe har pichhle token ki keys aur values dobara nikalni padengi, jo bekaar hai. KV cache ab tak ki keys aur values store karta hai, to har step mein sirf naye token ki nikalni padti hain. Isse generation kaafi tez hota hai, par cache bahut GPU memory leta hai, jo sequence length aur batch size ke saath badhti hai, isliye grouped query attention aur paged attention, jaise vLLM mein, zaroori hain.

✅

  • Generation ke dauraan pichhli keys aur values store
  • Dobara calculation nahi; badi speedup
  • GPU memory leta hai; length aur batch ke saath badhta hai
  • GQA aur paged attention us memory ko sambhaalte hain

: Inference ki buniyaad, labs aur LLM infra teams poochhti hain.

Post-training quantisation (INT8/INT4, AWQ, GPTQ) kaise kaam karta hai, aur activation outliers naive INT4 ko kyun tod dete hain?

💬

Quantisation 16-bit floating-point weights (FP16/BF16) ko scale factor ki madad se 8-bit ya 4-bit integers ke chhote grid pe map karta hai, jisse GPU memory 2× se 4× kam lagti hai aur memory-bandwidth se bandha token generation tez ho jaata hai. Naive round-to-nearest INT4 accuracy gira deta hai kyunki ~6B parameters se upar transformer activations mein kuch bade outlier channels (normal se 100× bade) ban jaate hain; 16 integer buckets ko us range pe failane se saare normal weights zero mein dab jaate hain. AWQ aur GPTQ chhote calibration set se ise theek karte hain: AWQ quantise karne se pehle un 1% weight channels ko scale up karke bacha leta hai jo bade activation outliers se multiply hote hain.

✅

  • FP16/BF16 weights ko INT8/INT4 grids pe map karta hai; VRAM 2–4× kam aur token decoding tez
  • Transformer activation outliers quantisation grid ko kheench ke normal values daba dete hain
  • AWQ / GPTQ calibration data se zaroori weight channels ko bachaate hain
  • Lambe contexts aur bade batch sizes ke liye KV cache (FP8/INT8) bhi quantise karo

: LLM efficiency aur quantisation ki gehri samajh check karta hai.

Open source LLM ko GPUs pe efficiently kaise serve karoge?

💬

Plain web server ke bajaye LLM ke liye bana inference server use karo, jaise vLLM ya TGI. Inme continuous batching hoti hai, jo chalte batch mein nayi requests jodti hai taaki GPU busy rahe, aur KV cache memory sambhaalne ke liye paged attention. Quality poori karne wala sabse chhota model chuno, aur saste GPUs pe fit karne ke liye 8 bit ya 4 bit quantisation socho. Phir queue length ya tokens per second pe autoscale karo, max token limits lagao, aur time to first token, tokens per second, GPU memory aur per request cost monitor karo.

✅

  • LLM inference server (vLLM, TGI)
  • Continuous batching, paged KV cache
  • Sahi size aur quantised models
  • Autoscale aur latency, throughput, cost monitor

: LLM infrastructure ab zyaadatar MLOps interviews ka hissa hai.

LLM gateway mein distributed tracing, prompt caching, semantic caching aur model routing ek saath kaise kaam karte hain?

💬

Har user request ko ek trace ID milti hai aur query rewriting, retrieval, reranking, LLM calls aur tool calls ke liye child spans, jo exact inputs, outputs, latency, token counts aur cost record karte hain. Gateway mein prompt/prefix caching static system instructions aur few-shot examples ka KV cache requests ke beech dobara use karta hai, jisse input token cost 50–90% ghat jaati hai. Semantic caching query ko embed karke milte-julte repeat FAQs ke liye jaancha hua cached jawaab deta hai (tenant aur permissions ke hisaab se alag). Aakhir mein model router 70–80% simple classification ya FAQ queries ko tez, saste chhote model pe bhejta hai aur sirf mushkil reasoning ko frontier model pe, aur provider 429 ya 503 de to automatic fallback karta hai.

✅

  • Trace + child spans har step pe latency, tokens, cost aur prompt version pakadte hain
  • Prompt/prefix caching static system prompts aur examples ka KV cache dobara use karta hai
  • Semantic caching repeat FAQs serve karta hai (tenant/permissions aur freshness se bandha)
  • Model routing simple traffic chhote models pe bhejta hai + automatic provider fallbacks

: 2026 ka core LLMOps aur AI Platform architecture sawaal.

1,000 requests per second pe LLM serve karne wala platform design karo.

💬

Model size, prompt aur output length, aur latency targets clarify karo, khaaskar time to first token. Requests ek gateway se jaati hain jisme authentication, har customer ki rate limits aur routing ho. Uske peeche GPU servers ka pool jo vLLM jaisa inference engine continuous batching aur paged KV cache ke saath chalata hai, queue depth pe autoscale. Repeat prompts ke liye prefix aur response cache, aur simple requests chhote model pe. Har GPU ke tokens per second se capacity estimate karo, peak ke liye headroom rakho, aur zones mein faila do. Time to first token, tokens per second, queue time, errors aur per thousand tokens cost monitor karo, aur naye model versions canaries se rollout.

✅

  • Sizes aur latency targets clarify
  • Gateway: auth, rate limits, routing
  • Batching wala inference engine, queue pe autoscaling
  • Caching, model routing, capacity planning, monitoring, canaries
