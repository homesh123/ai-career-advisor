🕸️ Bharosemand agent workflows: state graphs, memory, human-in-the-loop aur recovery

EnglishHinglish

🏠 Asli zindagi ki misaal

Agar kisi naye intern ko bas itna bol do ki 'customer complaints sambhal lo', to woh ghabra kar galat department ko paanch baar phone kar sakta hai ya ₹50,000 ka refund de sakta hai. Ek anubhavi team saaf flowchart pe chalti hai: ticket padho → order dekho → agar refund < ₹500 hai to auto-process, warna manager ki manzoori ke liye ruko → jawaab bhejo. State graphs AI agents ko wahi bharosemand flowchart, checkpoints aur human approval gates dete hain.

💡 Aasaan shabdon mein

Khule ReAct agent loops lachile hote hain, par production mein woh infinite loop mein phans sakte hain, crash pe state bhool sakte hain, ya galat arguments ke saath tool call kar sakte hain. Production teams saaf state graphs (jaise LangGraph) banati hain: nodes steps hote hain (LLM call, tool run, validation) aur edges tay karte hain aage kahan jaana hai. State ko ek typed object mein database pe save rakho (checkpointing) taaki agent kisi risky kaam (jaise refund dena ya email bhejna) se pehle insaan ki manzoori (human-in-the-loop) ke liye ruk sake aur ghanton baad wahin se aage badhe. Short-term memory (abhi ka task) aur long-term memory (user preferences) alag rakho, max steps ki limit lagao, aur har tool argument ko schema se check karo.

🎬 Dekho kaise kaam karta hai

State graph agent ko safe patari pe rakhta hai: chhote kaam apne aap chalte hain, jabki risky actions checkpoint pe ruk kar insaan ki approval ka wait karte hain.

🪜 Step by step

  1. Sabse simple pattern se shuru karo: jab steps pehle se pata hon, tab ek LLM call ya tay 3-step pipeline autonomous agent se behtar hota hai.
  2. Multi-step workflows ko saaf state graph ki tarah banao: ek typed State object aur chhote node functions jo state padhein aur update karein.
  3. Code mein pakke safety guards lagao: max_steps (jaise 8), token/cost limit, tool timeouts, aur ek hi tool call repeat hone par cycle detection.
  4. Har node ke baad Postgres/Redis mein state checkpoint save karo taaki write/delete action se pehle workflow insaan ki approval ke liye ruk sake.
  5. Poore execution traces (har prompt, tool input/output, latency aur tokens) log karo aur 30+ asli scenarios pe agent ko test karo.

🔑 Zaroori shabd

State graph (LangGraph)
Nodes aur conditional edges ka saaf graph jo control karta hai ki agent ek step se doosre step pe kaise jaaye.
Checkpointing
Har step ke baad agent ki state save karna taaki woh crash se ubhar sake ya insaan ki approval ke liye ruk sake.
Router / orchestrator-worker
Aisa pattern jahan ek router har sub-task ko ek bade prompt ke bajaye chhote specialist workflow ke paas bhejta hai.

👀 Example dekho

text
Support Agent State Graph (max_steps = 6):
  [Classify] → [Fetch Order Tool] → [Draft Reply]
                                         │
                 ┌───────────────────────┴───────────────────────┐
          refund <= ₹500                                  refund > ₹500
                 ▼                                               ▼
        [Execute Refund]                              [Pause: Human Approval]
                 └───────────────────────┬───────────────────────┘
                                         ▼
                                   [Send Reply]

Code safety boundaries control karta hai; LLM classification, tool parameters aur drafting sambhalta hai.

⚠️ Aam galtiyaan jinse bachna hai

  • Bina step limit ke 5 agents ka 'autonomous crew' banana jo aapas mein baat karke 50,000 tokens jala dein, jabki 3-node workflow wahi kaam 2 second mein kar de.
  • Strict Pydantic tool schemas aur parameterised queries ke bajaye agent ko seedha SQL ya shell command mein unvalidated text bhejne dena.

✅ Jaldi se check karo

Ek business workflow hamesha tay order mein wahi 4 steps leta hai, jismein ek LLM call fields nikalta hai aur doosra summary likhta hai. Aapko kya banana chahiye?

  1. Ek deterministic workflow / state graph jo sirf un do steps pe LLM call kare jahan uski zaroorat hai
  2. Ek poori tarah autonomous multi-agent swarm jo aapas mein behas kare
  3. Shuru se train kiya hua naya model
Jawaab dekho

A. Ek deterministic workflow / state graph jo sirf un do steps pe LLM call kare jahan uski zaroorat hai: Tay workflows khule autonomous loops ke mukaable tez, saste, predictable aur debug karne mein kahin aasaan hote hain.

🙋 Seekhne wale yeh poochhte hain

Agent mein short-term aur long-term memory kaise sambhalni chahiye?

Short-term memory (abhi ke messages aur tool results) graph state mein rakho aur summarise hone ke baad purane bhaari tool outputs chhota kar do. Long-term facts database mein rakho aur zaroorat pe hi nikalo.

Workflow ke beech mein koi tool fail ho jaaye to kya karein?

Temporary errors (429/503) ko tool wrapper mein retry karo; business errors pe saaf message state graph ko do taaki woh ek baar sudhaar kare ya insaan ko saunp de.

🎯 Is topic pe interviews mein poochhe jaane wale sawaal

Pehle khud bolkar jawaab dene ki koshish karo, phir model answer kholo.

MCP Host–Client–Server architecture kaise kaam karta hai, aur enterprise production mein MCP tools ko kaise secure karte ho?

💬

MCP mein Host AI app hai (jaise IDE ya support assistant), Client host ke andar 1-to-1 protocol connection rakhta hai, aur Server teen primitives deta hai: Resources (read-only context), Prompts (templates) aur Tools (chalne wale actions). Production mein secure karne ke liye main MCP server ko kabhi shared admin database key nahi deta; main logged-in user ka OAuth token ya scope bhejta hoon taaki har query row-level permissions maane. Main destructive tools pe confirmation gates lagata hoon taaki writes se pehle insaan approve kare, aur indirect prompt injection se bachne ke liye tool outputs sanitise karta hoon.

✅

  • Host (app) → Client (1:1 connector) → Server (Resources, Prompts, Tools)
  • Per-user identity aur least-privilege scopes, kabhi shared admin key nahi
  • Destructive tool calls se pehle human-in-the-loop approval
  • Untrusted tool outputs sanitise karo aur audit ke liye har call log karo

Agent banate waqt open-ended ReAct loop ke bajaye explicit state graph (jaise LangGraph) kyun use karte hain?

💬

Open-ended ReAct loop LLM ko har agla step khul ke tay karne deta hai, jo flexible exploration ke liye theek hai par production mein aksar gol-gol ghoomta rehta hai, fields bhool jaata hai ya safety steps chhod deta hai. State graph ek typed state object, chhote deterministic ya LLM nodes jo us state ko update karein, aur explicit conditional edges define karta hai jo tay karte hain kaunsa transition allowed hai. Isse persistent checkpoints milte hain taaki lamba workflow human approval click ke liye ruk sake aur ghanton baad wahin se shuru ho, infinite loops rokne ke liye hard step aur token budgets, aur saaf per-node traces.

✅

  • Typed shared state + chhote nodes + explicit conditional edges
  • Gair-kanooni transitions aur infinite tool-calling loops rokta hai
  • Checkpointing se pause/resume aur human-in-the-loop approval gates milte hain
  • Side-effect wale tools pe idempotency keys taaki retries double charge na karein

: 2026 ka signature agent engineering sawaal: production mein autonomy ko control karna.

Ek AI agent design karo jo customer support sambhaale, refunds samet.

💬

Scope clarify karo: kaunsi requests, kaunse systems, refund limits, bhashaayein. Architecture: agent ko order dhoondhna, refund policy check karna, refund banana aur insaan ko handoff jaise tools milte hain, har ek validated parameters aur least privilege ke saath. Policy code mein enforce hoti hai, sirf prompt mein nahi: jaise ₹2,000 se upar ya policy se bahar refunds hamesha human approval maangte hain. Help articles pe RAG se jawaab ground karo. Prompt injection ke khilaaf guardrails, aur account ke kisi action se pehle identity verification. Sandbox mein asli recorded conversations se evaluate karo: sahi resolution, galat actions, escalation rate aur per conversation cost. Pehle ek category ke liye launch, insaan sample review karein.

✅

  • Scope aur limits clarify
  • Least privilege tools; policy code mein
  • Risky actions ke liye human approval; identity checks
  • Sandbox evals; phased launch; metrics
