🚦 Prompt changes safely ship karna: versioning, CI mein evals aur dheere rollout

EnglishHinglish

🏠 Asli zindagi ki misaal

Naye laddoo ki recipe test karti mithai ki dukaan Diwali ki subah saare dabbe nahi badalti. Woh recipe version number ke saath likhti hai, staff se purani recipe ke mukaable chakhwati hai, pehle ek branch mein bechti hai, aur customers shikaayat karein to purani recipe tayyar rakhti hai. Prompts ko bhi yahi dhyaan chahiye, kyunki ek line ka prompt badlaav aapke product ka har jawaab badal sakta hai.

💡 Aasaan shabdon mein

Prompts, model names aur settings (temperature, tools, retrieval settings) ko code ki tarah treat karo. Unhe version control ya prompt registry mein version ID ke saath rakho, aur har request ke saath woh ID log karo taaki pata chale kis version ne jawaab diya. Change merge karne se pehle CI mein apna eval set apne aap chalao: golden questions, format checks, safety tests aur LLM-as-judge scores, current version ke mukaable, ek rule ke saath jaise "koi metric 2 points se zyaada na gire". Sirf average nahi, failures dekho. Phir dheere release karo: naye version ko feature flag ke peeche rakho, 5% traffic usko bhejo (canary), online signals dekho jaise thumbs down, edits, escalations, latency aur cost, phir badhao. Kuch galat ho to flag badal kar rollback karo, bina redeploy. Model khud upgrade karna bhi isi tarah ka change hai: pehle evals chalao, kyunki naya model bhi aapke kaam pe alag behave kar sakta hai. Ek chhota changelog rakho ki har version kyun badla.

🎬 Dekho kaise kaam karta hai

Naye prompt version ko CI mein eval gate paas karna hota hai, phir flag ke peeche 5% users ko jaata hai. Online signals theek rahein to 25% aur 100% tak badhta hai; nahi to ek switch se rollback.

🪜 Step by step

  1. Prompts ko bikhri strings se nikaal kar versioned files ya prompt registry mein rakho, har ek ki ID jaise support@v14.
  2. Har request ke saath prompt version aur model log karo taaki har jawaab ka pata lagaaya ja sake.
  3. CI mein eval job jodo jo candidate ko current version se compare kare aur tay regressions pe pull request fail kare.
  4. Sirf scores nahi, badle hue jawaabon ka sample saath saath dekho.
  5. Feature flag ke peeche 5% traffic ko release karo, ek do din online signals dekho, phir steps mein badhao.
  6. Rollback ek switch pe rakho, aur har version ki changelog entry likho.

🔑 Zaroori shabd

Prompt registry
Prompts aur model settings ka versioned store jise app ID se load karta hai.
Eval gate in CI
Automatic check jo eval scores tay rule se neeche girne par change rok deta hai.
Canary release
Pehle thoda sa traffic naye version ko bhejna aur dhyaan se dekhna.
Feature flag
Switch jo bina redeploy kuch users ke liye version on ya off karta hai.

👀 Example dekho

yaml
# .github/workflows/prompt-evals.yml
on: pull_request
jobs:
  evals:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm ci
      - run: npm run evals -- --candidate prompts/support@v14 --baseline prompts/support@v13
      # fails the PR if: faithfulness drops > 2 pts, format errors > 0, safety tests fail

# After merge: flags.support_prompt = { v14: 5%, v13: 95% }
# Watch thumbs-down rate, escalations, p95 latency, cost/request for 48 h → 25% → 100%
# Problem? set v14: 0% (instant rollback, no redeploy)

Prompt ko version karo, CI mein evals se gate karo, flag ke peeche 5% pe release karo, phir aage badhao ya wapas lo.

⚠️ Aam galtiyaan jinse bachna hai

  • Shukravaar shaam production mein seedha prompt edit karna kyunki "sirf text hai".
  • Bina evals chalaaye naye model pe upgrade karna, yeh maan kar ki naya hamesha aapke kaam ke liye behtar hai.
  • Aisa eval set jo kabhi nahi badhta, to production ke naye failure types nikalte rehte hain.

✅ Jaldi se check karo

Ek teammate ne support prompt sudhaara aur woh behtar padhta hai. Sab users tak pahunchne se pehle kya hona chahiye?

  1. CI mein current version ke mukaable eval set chalao, phir flag ke peeche thode traffic ko release karo
  2. Sabko ship kar do kyunki behtar padhta hai
  3. Model se poocho ki naya prompt behtar hai ya nahi
Jawaab dekho

A. CI mein current version ke mukaable eval set chalao, phir flag ke peeche thode traffic ko release karo: Behtar padhne wala prompt bhi formats ya zaroori cases tod sakta hai. Evals release se pehle regressions pakadte hain, aur canary jo chhoot jaaye uska nuksaan seemit rakhta hai.

🙋 Seekhne wale yeh poochhte hain

CI eval set kitna bada hona chahiye?

Aam, mushkil aur risky inputs wale 50 se 200 cases se shuru karo, aur har asli failure jo theek karo use jodo. Itna tez rakho ki har pull request pe chal sake.

Kya CI mein LLM-as-judge scores pe bharosa kar sakte hain?

Kuch had tak. Pehle judge ko human labels se check karo, saaf rubrics use karo, aur exact checks (format, zaroori facts) ke saath milao jinhe judge ki zaroorat nahi.

🎯 Is topic pe interviews mein poochhe jaane wale sawaal

Pehle khud bolkar jawaab dene ki koshish karo, phir model answer kholo.

Prompt ka change, ya model upgrade, users ke liye kuch tode bina kaise ship karoge?

💬

Main prompts aur model settings ko code ki tarah treat karta hoon. Woh version control ya prompt registry mein version ID ke saath rehte hain, aur har request log karti hai ki kis version ne jawaab diya. Prompt badalne wala pull request CI mein current version ke mukaable eval set chalata hai: golden questions, format checks aur safety tests, ek rule ke saath jaise koi metric do points se zyaada na gire. Badle hue jawaabon ka sample bhi padhta hoon. Merge ke baad naya version feature flag ke peeche lagbhag 5% traffic pe jaata hai, hum thumbs down, edits, escalations, latency aur cost dekhte hain, phir steps mein badhaate hain. Rollback ek switch hai. Model upgrade bhi bilkul isi process se guzarta hai.

✅

  • Prompts versioned aur har request pe log
  • CI mein current version ke mukaable eval gate
  • Sirf scores nahi, badle jawaab padho
  • Feature flag ke peeche canary, online signals dekho
  • Ek switch rollback; model upgrades bhi isi raaste

: Kya aap bina regressions ke tezi se iterate kar sakte ho.
