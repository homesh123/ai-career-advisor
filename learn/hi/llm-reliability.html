🛟 Reliability: timeouts, retries, fallbacks aur rate limits

EnglishHinglish

🏠 Asli zindagi ki misaal

Jab aapka roz ka auto wala phone nahi uthata, aap gate pe ek ghanta intezaar nahi karte. Thoda rukte ho, ek baar aur call karte ho, phir cab book karte ho, aur kuch na chale to bus le lete ho. Reliable AI feature ka bhi yahi plan hota hai: time limit, samajhdaar retry, backup model aur kuch na chale to bhi kaam ki screen.

💡 Aasaan shabdon mein

Model APIs normal tareekon se fail hoti hain: rate limits (HTTP 429), overloaded servers (5xx), slow responses aur kabhi kabhi outages. Har ek ke liye plan rakho. Har call pe timeout lagao, interactive features ke liye chhota. Sirf woh errors retry karo jo theek ho sakte hain (429, 5xx, timeouts), exponential backoff aur jitter ke saath, zyaada se zyaada do teen baar, aur Retry-After header maano; 400 bad request ko bina badle kabhi retry mat karo. Actions idempotent banao taaki retry se do emails ya do refunds na chale jaayein: idempotency key use karo. Fallback chain rakho: usi kaam ke liye doosra model ya provider, phir cached ya simple jawaab, phir saaf message ke saath non-AI raasta (template, search box, "insaan se baat karo"). Model ke aage apni rate limits aur per-user budgets lagao taaki ek user ya ek bug aapka quota khatam na kar de. Circuit breaker use karo: agar provider baar baar fail ho, ek minute ke liye use call karna band karo aur fallback chalao. Error rate, retries aur fallback rate dashboard pe alerts ke saath track karo, aur failure ke raaste jaan boojh kar test karo.

🎬 Dekho kaise kaam karta hai

Call time out hota hai ya 503 milta hai. App badhte intezaar ke saath retry karta hai, phir circuit breaker backup model pe switch karta hai, aur woh bhi fail ho to users ko kaam ka non-AI raasta milta hai.

🪜 Step by step

  1. Har model aur tool call pe timeout lagao, interactive screens ke liye background jobs se chhota.
  2. Sirf temporary errors (429, 5xx, timeouts) retry karo, exponential backoff, jitter aur do teen tries ki limit ke saath; Retry-After maano.
  3. Kuch badalne wale har action (email, refund, ticket) ko idempotency key do taaki retries use dohra na sakein.
  4. Har feature ki fallback chain tay karo: backup model, cached ya simple jawaab, phir saaf message ke saath non-AI raasta.
  5. Model ke aage per-user rate limits aur daily budgets lagao, aur har provider ke liye circuit breaker.
  6. Error rate, fallback rate aur budget pe alert lagao, aur failures jaan boojh kar test karo (staging mein provider block karke dekho users ko kya dikhta hai).

🔑 Zaroori shabd

Exponential backoff
Har fail try ke baad zyaada rukna (1 s, 2 s, 4 s), thodi randomness (jitter) ke saath.
Fallback chain
Backup ka order: doosra model, cached ya simple jawaab, phir non-AI raasta.
Circuit breaker
Fail hoti service ko thodi der call karna band karta hai taaki app tez rahe aur sambhal jaaye.
Idempotency key
Har action ki unique ID taaki retry hui request do baar na chale.

👀 Example dekho

python
RETRYABLE = {429, 500, 502, 503, 504}

def generate_with_fallback(prompt):
    for provider in [primary, backup]:                 # fallback chain
        if breaker.is_open(provider):
            continue                                   # skip a provider that keeps failing
        for attempt in range(3):
            try:
                return provider.generate(prompt, timeout=8)
            except ApiError as e:
                if e.status not in RETRYABLE:
                    raise                              # a 400 won't fix itself
                time.sleep(e.retry_after or (2 ** attempt + random.random()))
            except Timeout:
                pass
        breaker.record_failure(provider)
    return SAFE_FALLBACK_MESSAGE                       # template + "talk to a human"

Har call pe timeout, sirf theek ho sakne wale errors backoff ke saath retry, toote providers chhodo, aur hamesha kaam ke fallback pe khatam karo.

⚠️ Aam galtiyaan jinse bachna hai

  • Rate limit ke dauraan turant tight loop mein retry karna, jisse overload aur badhta hai aur aap zyaada der block hote ho.
  • Aise agent step ko retry karna jo email bhej chuka tha, to customer ko do baar milti hai.
  • Model down hone pe khaali screen ya raw stack trace, kaam ke fallback ki jagah.

✅ Jaldi se check karo

Aapka model call HTTP 400 (bad request) se fail hota hai. Code ko kya karna chahiye?

  1. Retry mat karo; log karo, request theek ya validate karo, aur fallback dikhao
  2. Backup provider pe wahi request bhej do
  3. Backoff ke saath paanch baar retry karo
Jawaab dekho

A. Retry mat karo; log karo, request theek ya validate karo, aur fallback dikhao: 400 ka matlab request hi galat hai, isliye dohraane se har baar fail hogi aur paisa barbaad hoga. Retries 429, 5xx aur timeouts jaise temporary errors ke liye hain.

🙋 Seekhne wale yeh poochhte hain

Kya do model providers use karne chahiye?

Zaroori features ke liye haan: ek tested backup model rakho aur uspe bhi evals chalao, kyunki prompts models ke beech hamesha perfectly kaam nahi karte.

AI feature ke liye accha timeout kitna hai?

User ke sabr aur apne p99 ke hisaab se: streaming jawaab ke liye aksar 10 se 20 second (pehla token 2 se 3 second mein) aur background jobs ke liye zyaada.

🎯 Is topic pe interviews mein poochhe jaane wale sawaal

Pehle khud bolkar jawaab dene ki koshish karo, phir model answer kholo.

Peak hour mein model provider ka outage ho jaata hai. Aapka AI feature kaise behave kare, aur aap ise kaise banaoge?

💬

Users ko phir bhi kuch kaam ka milna chahiye aur kuch bhi tootna ya dohraana nahi chahiye. Har call pe timeout hota hai. Main sirf temporary errors retry karta hoon, 429, 5xx aur timeouts, exponential backoff, jitter aur chhoti limit ke saath, aur Retry-After maanta hoon. Circuit breaker baar baar fail hote provider ko call karna rok deta hai, aur fallback chain sambhaalti hai: tested backup model, phir cached ya simple jawaab, phir saaf message ke saath non-AI raasta jaise template ya insaan se baat. Kuch badalne wale actions idempotency key ke saath chalte hain taaki retries do refunds na bhej dein. Per-user rate limits, error aur fallback rates pe alerts bhi hain, aur main staging mein outage ka raasta jaan boojh kar test karta hoon.

✅

  • Har call pe timeout
  • Sirf temporary errors backoff aur limit ke saath retry
  • Circuit breaker aur non-AI raaste pe khatam hoti fallback chain
  • Actions ke liye idempotency keys
  • Alerts aur jaan boojh kar failure testing

: Production ki maturity: sirf happy path nahi, failure ke liye design.

📌 Yaad rakho

Timeouts, sirf temporary errors pe retries, idempotent actions, fallback chain aur apni rate limits.
