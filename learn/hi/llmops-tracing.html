📡 LLMOps: tracing, model routing, caching aur cost va latency ghataana

EnglishHinglish

🏠 Asli zindagi ki misaal

Hospital ke triage desk aur courier tracking number ke baare mein socho. Mamooli zukhaam wale har mareez ko bade neurosurgeon ki zaroorat nahi hoti: triage desk aasaan cases general doctor ko aur mushkil cases specialist ko bhejta hai. Yahi model routing hai. Aur jab parcel late ho, to tracking number dikhata hai ki woh kis hub pe kab ruka. Yahi LLM tracing hai.

💡 Aasaan shabdon mein

Production mein user ka ek sawaal query rewriting, embedding search, reranking, do tool calls aur aakhri LLM answer chala sakta hai. Bina tracing (OpenTelemetry, Langfuse, Arize Phoenix) ke aap nahi bata sakte kaunsa step slow tha ya jawaab kahan galat hua. Trace har andar ke step (span) ka prompt version, input, output, tokens, kharch aur latency record karta hai. Latency aur kharch 50–80% ghataane ke liye: (1) tokens stream karo taaki Time to First Token (TTFT) 500 ms se kam rahe, (2) lambe system prompts ke liye prompt/prefix caching use karo, (3) baar-baar poochhe jaane wale sawaalon ke liye semantic caching lagao, aur (4) LLM gateway aur model routing use karo — aasaan classification/extraction chhote tez model ko bhejo aur frontier model sirf mushkil reasoning ke liye rakho.

🪜 Step by step

  1. Har LLM call, retrieval query aur tool execution ko trace ID aur child spans ke saath log karo (prompt version, model, tokens, kharch aur latency samet).
  2. Time to First Token (TTFT) aur tokens-per-second ko kul latency se alag naapo, aur UI mein responses stream karo.
  3. Static instructions, tool definitions aur examples ko har prompt ke shuru mein rakho taaki prefix caching se input kharch aur TTFT 50–80% ghat jaaye.
  4. Providers ke aage ek LLM gateway lagao jo rate limits, retries, fallback models aur team cost budgets sambhale.
  5. Complexity ke hisaab se requests route karo: aasaan intents aur extraction chhote tez model se karwao, aur sirf mushkil sawaal frontier model ko bhejo.

🔑 Zaroori shabd

Trace & spans
Ek user request ka poora record (trace), jismein har LLM, retrieval aur tool step (span) ki latency aur tokens darj hote hain.
Prompt / prefix caching
Shared static prefix (system prompt + examples) ka KV cache reuse karna taaki kharch aur TTFT dono ghatein.
Model routing / cascading
Aasaan sawaal chhote saste model ko bhejna aur sirf mushkil sawaal bade frontier model ko dena.

👀 Example dekho

text
Trace tr_9821 (total: 640 ms, $0.0008):
  ├─ Span 1: Semantic cache check          12 ms  (MISS)
  ├─ Span 2: Router (small 8B model)       68 ms  → intent = 'order_status' (simple)
  ├─ Span 3: Tool get_order(#A123)         45 ms  → {status: 'Out for delivery'}
  └─ Span 4: Fast model response (prefix cached, TTFT 180 ms, 515 ms total)

Tracing har step ka waqt dikhata hai, aur routing + prefix caching TTFT aur kharch dono kam rakhte hain.

⚠️ Aam galtiyaan jinse bachna hai

  • System prompt ki pehli hi line mein badalta hua timestamp ya user ID daal dena, jisse har request pe prefix cache toot jaata hai!
  • Bina tenant_id ya user permissions check kiye semantic cache lagana, jisse ek customer ka cached jawaab galti se doosre ko chala jaaye.

✅ Jaldi se check karo

Provider ki prompt/prefix caching ka fayda uthaane ke liye aapke static system instructions aur examples prompt mein kahan hone chahiye?

  1. Har request pe randomly ghuma kar
  2. Bilkul shuru mein (ekdum same prefix), aur user ka badalta hissa aakhir mein
  3. Bilkul aakhir mein, user ke badalte sawaal ke baad
Jawaab dekho

B. Bilkul shuru mein (ekdum same prefix), aur user ka badalta hissa aakhir mein: KV-cache reuse sirf pehle badalne wale token tak kaam karta hai, isliye static hissa hamesha sabse aage hona chahiye.

🙋 Seekhne wale yeh poochhte hain

Prefix caching aur semantic caching mein kya fark hai?

Prefix caching shared prompt ke aage ke hisse ka GPU KV-cache reuse karta hai aur naya jawaab banata hai. Semantic caching user ke sawaal ko embed karta hai aur agar bilkul waisa hi sawaal pehle aa chuka ho, to bina LLM call kiye save kiya hua jawaab de deta hai.

LLM latency mein achanak 2× uchaal aaye to kaise debug karein?

Apne trace spans ka p95 time dekho: kya retrieval/reranking slow hua, kya prompt badalne se output tokens dugne ho gaye, ya provider ka TTFT gira hai?

🎯 Is topic pe interviews mein poochhe jaane wale sawaal

Pehle khud bolkar jawaab dene ki koshish karo, phir model answer kholo.

Aapka LLM feature bahut slow aur mehenga hai. Kya karoge?

💬

Pehle naapta hoon tokens aur time kahan ja rahe hain: prompt size, output size, calls ki ginti. Phir main levers: response stream karo taaki user ko turant text dikhe; prompts aur retrieved context chhote karo; repeat sawaalon ke jawaab cache karo aur lambe fixed system prompts ke liye prompt caching; aasaan requests chhote, saste model pe aur sirf mushkil wali bade model pe bhejo; agent steps kam karo; aur background jobs batch karo. Har change ke baad evals dobara chalao, taaki quality na gire.

✅

  • Pehle naapo: tokens, calls, har step ka time
  • Feel hone wali speed ke liye streaming
  • Chhota context, caching, routing se chhote models, kam steps
  • Har change ke baad evals se quality check

: Cost aur latency ke trade offs 2026 ka bada topic hain.

LLM applications chalaana classic ML models se kaise alag hai?

💬

Kai nayi cheezein sambhaalni padti hain. Prompts code hain, to unhe versioning, review aur testing chahiye. Har prompt ya model change pe evaluation suites chalni chahiye, kyunki ek accuracy number nahi hota. Cost per request aur per feature monitor karni padti hai, kyunki tokens ke saath badhti hai. Providers models update karte hain, to versions pin karta hoon aur upgrade se pehle evals dobara chalata hoon. Chain ya agent ke har step ki logging aur tracing debugging ke liye zaroori hai. Aur safety checks: prompt injection, logs mein personal data, aur content filters.

✅

  • Prompt versioning aur testing
  • Release gates ke roop mein eval suites
  • Token cost monitoring
  • Model version pinning, tracing, safety controls

: 2026 mein interviews mein LLMOps badh raha hai.

LLM gateway mein distributed tracing, prompt caching, semantic caching aur model routing ek saath kaise kaam karte hain?

💬

Har user request ko ek trace ID milti hai aur query rewriting, retrieval, reranking, LLM calls aur tool calls ke liye child spans, jo exact inputs, outputs, latency, token counts aur cost record karte hain. Gateway mein prompt/prefix caching static system instructions aur few-shot examples ka KV cache requests ke beech dobara use karta hai, jisse input token cost 50–90% ghat jaati hai. Semantic caching query ko embed karke milte-julte repeat FAQs ke liye jaancha hua cached jawaab deta hai (tenant aur permissions ke hisaab se alag). Aakhir mein model router 70–80% simple classification ya FAQ queries ko tez, saste chhote model pe bhejta hai aur sirf mushkil reasoning ko frontier model pe, aur provider 429 ya 503 de to automatic fallback karta hai.

✅

  • Trace + child spans har step pe latency, tokens, cost aur prompt version pakadte hain
  • Prompt/prefix caching static system prompts aur examples ka KV cache dobara use karta hai
  • Semantic caching repeat FAQs serve karta hai (tenant/permissions aur freshness se bandha)
  • Model routing simple traffic chhote models pe bhejta hai + automatic provider fallbacks

: 2026 ka core LLMOps aur AI Platform architecture sawaal.

1,000 requests per second pe LLM serve karne wala platform design karo.

💬

Model size, prompt aur output length, aur latency targets clarify karo, khaaskar time to first token. Requests ek gateway se jaati hain jisme authentication, har customer ki rate limits aur routing ho. Uske peeche GPU servers ka pool jo vLLM jaisa inference engine continuous batching aur paged KV cache ke saath chalata hai, queue depth pe autoscale. Repeat prompts ke liye prefix aur response cache, aur simple requests chhote model pe. Har GPU ke tokens per second se capacity estimate karo, peak ke liye headroom rakho, aur zones mein faila do. Time to first token, tokens per second, queue time, errors aur per thousand tokens cost monitor karo, aur naye model versions canaries se rollout.

✅

  • Sizes aur latency targets clarify
  • Gateway: auth, rate limits, routing
  • Batching wala inference engine, queue pe autoscaling
  • Caching, model routing, capacity planning, monitoring, canaries

: LLM infrastructure system design.

Kal se aapke AI feature ka response time double ho gaya. Kaise investigate karoge?

💬

Check karo kya badla: deploys, prompt changes, model version change, ya provider ka status issue. Phir traces se dhoondho kaunsa step slow hua: retrieval, LLM call, tool call ya humara code. Agar LLM call hai, to dekho prompts ya outputs lambe hue ya nahi, jaise bada retrieved context ya aisa prompt change jo jawaab lambe karta hai, ya provider ki latency badhi. Agar humara hai, to database queries, cache hit rate aur traffic volume dekho. Wajah theek karo, zaroorat ho to rollback, aur har step pe latency alert jodo taaki agli baar jaldi pakde.

✅

  • Kya badla? deploys, prompts, models, provider
  • Har step ke traces se jagah dhoondho
  • Token count badalna common wajah
  • Theek ya rollback; har step pe alerts
