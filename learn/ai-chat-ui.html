💬 Building AI chat UIs: streaming, stop, retry and generative UI

EnglishHinglish

🏠 Real-life example

Think of a chai stall versus a restaurant that brings everything only when the full thali is ready. At the chai stall you watch your tea being made, you can say "less sugar" midway, and you get the first sip quickly. A good AI chat UI is the chai stall: words appear as they are written, the user can press Stop, ask again, or edit their question, and nothing feels frozen.

💡 In simple words

An AI chat screen has more state than a normal form. Each message has a role (user or assistant), content that grows while streaming, and a status: pending, streaming, done, stopped or failed. The server calls the model with stream on and forwards chunks to the browser using Server-Sent Events (SSE) or a streamed HTTP response; the browser appends each chunk to the last assistant message. Users must be able to stop a long answer (an AbortController cancels the request and the model call, so you stop paying), regenerate an answer, and edit an earlier question. Render the answer as safe Markdown (sanitise HTML so a model can't inject a script), keep the scroll pinned to the bottom only while the user hasn't scrolled up, and show tool activity such as "Searching your orders…". Generative UI goes one step further: when the model calls a tool, the UI renders a real component (an order card, a chart, a form) instead of plain text. Libraries like the Vercel AI SDK (useChat, streamText) handle most of this for React and Next.js apps.

🎬 See how it works

The browser sends the question to your server route, the server streams the model's words back over SSE, and each word appears as it arrives. Stop cancels the request and the model call.

🪜 Step by step

  1. Model each message as { id, role, parts, status } where status is pending, streaming, done, stopped or failed, so the UI always knows what to show.
  2. On send, add the user message and an empty assistant message at once (optimistic UI), disable send, and show a typing indicator until the first token.
  3. Stream from a server route with SSE or a streamed response, append chunks to the assistant message, and throttle re-renders (for example every 50 ms) so long answers don't lag.
  4. Wire Stop to an AbortController that cancels the fetch and the model call; keep the partial text and mark it stopped. Add Regenerate and Edit question.
  5. Render Markdown with a sanitiser, highlight code with a copy button, and auto scroll only if the user is already at the bottom.
  6. Show tool steps as status lines ("Looking up order A12345…") and render tool results as components such as an order card, not raw JSON.
  7. Handle errors per message with a Retry button, save the conversation so a refresh doesn't lose it, and test on a slow 3G connection and a phone.

🔑 Key terms

SSE (Server-Sent Events)
A simple one way stream from server to browser, ideal for streaming tokens.
AbortController
The browser API that cancels an in-flight request when the user presses Stop.
Generative UI
Rendering real components from model tool calls, not just text.
Time to first token (TTFT)
How long until the first word appears; the number users feel most.

👀 See it in action

typescript
// app/api/chat/route.ts (Next.js + Vercel AI SDK)
import { streamText } from "ai";
import { anthropic } from "@ai-sdk/anthropic";

export async function POST(req: Request) {
  const { messages } = await req.json();
  const result = streamText({
    model: anthropic(process.env.CHAT_MODEL!), // model id kept in config, easy to upgrade
    system: "You are a helpful support assistant. Answer briefly.",
    messages,
    abortSignal: req.signal,          // Stop button cancels the model call too
  });
  return result.toUIMessageStreamResponse(); // streams chunks to the browser
}

// app/page.tsx
const { messages, sendMessage, stop, regenerate, status } = useChat();
// status: "submitted" | "streaming" | "ready" | "error"
// show <button onClick={stop}> while streaming, <button onClick={regenerate}> after

The server streams, the client appends, and Stop cancels both the request and the model call.

⚠️ Common mistakes to avoid

  • Rendering model output as raw HTML. A crafted answer or document can inject a script; always sanitise.
  • Stop only hides the text while the server keeps generating, so you still pay for tokens nobody reads.
  • Forcing the scroll to the bottom while the user is trying to read an earlier part of the answer.

✅ Quick check

A user presses Stop halfway through a long answer. What should happen?

  1. Delete the whole message and show an error
  2. Cancel the request and the model call, keep the partial text, and mark the message as stopped
  3. Hide the stream on screen but let the model keep generating in the background
Show answer

B. Cancel the request and the model call, keep the partial text, and mark the message as stopped: Aborting the model call saves cost and keeps the server free, and keeping the partial answer respects what the user already read.

🙋 Questions learners ask

SSE or WebSockets for streaming?

SSE (or a streamed HTTP response) is enough for model answers because data flows one way and it works through most proxies. Use WebSockets when the browser must also stream to the server, such as live voice.

Do I need the Vercel AI SDK?

No, but it saves time: it handles streaming formats, message state, tool calls and many providers. Learn how streaming works underneath once, then use whatever your team uses.

Should AI features always be a chat?

No. Many of the best AI features are a button inside an existing screen ("Summarise", "Draft reply") that streams into a panel. Use chat for open ended questions.

🎯 Asked in interviews on this topic

Try answering out loud first, then open the model answer.

Why do LLM products stream responses, and how would you implement it?

💬

Generating a full answer can take several seconds, but the first words are ready in a fraction of a second. Streaming shows text as it's generated, so the product feels fast even though total time is the same. To implement it, I call the LLM API with streaming on, read the chunks as they arrive on the server, and forward them to the browser with server sent events or a WebSocket, appending them to the UI. I handle a stop button, network errors mid stream, and I only run checks like JSON validation after the stream finishes.

✅

  • Time to first token vs total time
  • Server reads chunks, forwards via SSE or WebSocket
  • UI appends text; supports cancel
  • Validation and logging after completion
