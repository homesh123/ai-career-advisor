🏭 Training vs inference: how ML runs in production

EnglishHinglish

🏠 Real-life example

A chef spends months perfecting a recipe in a test kitchen. That's training: slow, expensive, done occasionally. Then the restaurant serves that dish to hundreds of customers a day, quickly and consistently. That's inference. Running AI in production is mostly about the restaurant, not the test kitchen.

💡 In simple words

Training uses lots of data and compute, often GPUs, to produce a model artifact: a saved file of learned parameters. Inference loads that artifact and makes predictions on new inputs, either in real time (an API answering in milliseconds) or in batches (scoring a million customers overnight). Inference has different priorities from training: latency, throughput, cost per request and reliability. Models are versioned like code, so you know exactly which model gave which answer. Infrastructure engineers usually own the inference side.

🪜 Step by step

  1. Training happens occasionally (daily, weekly) on lots of past data, often on powerful machines.
  2. The result is a saved model file plus its preprocessing steps, stored with a version.
  3. Inference uses that model to predict for new inputs, either in batches (score all customers nightly) or in real time (per request).
  4. Real time inference must be fast and reliable, so it runs behind an API with monitoring.
  5. Over time data changes, so you monitor results and retrain with fresh data.

🔑 Key terms

Model artifact
The saved, trained model file that gets deployed.
Inference
Using a trained model to make predictions.
Batch vs real-time
Scoring many items on a schedule vs answering each request instantly.

👀 See it in action

text
Training (weekly):   data → train.py on GPU → fraud_model_v12.pkl → registry
Inference (24×7):    UPI payment → API loads v12 → P(fraud)=0.03 → approve
                     latency budget: < 50 ms per payment

Same model, two very different engineering problems.

⚠️ Common mistakes to avoid

  • Saving the model without its preprocessing. Predictions break or silently go wrong in production.
  • Building real time serving when a nightly batch would do. Batch is simpler and cheaper.

✅ Quick check

Scoring all 2 million customers for churn risk every night is…

  1. Batch inference
  2. Real-time inference
  3. Training
Show answer

A. Batch inference: It's prediction (inference) done on a schedule over many items, which is batch.

🙋 Questions learners ask

Which costs more, training or inference?

For most companies, inference, because it runs constantly for every user. For LLMs, inference cost is the main bill unless you train your own models.

Does a model keep learning while in use?

Usually no. It's fixed until you retrain it. Online learning exists but is rarer and riskier.

🎯 Asked in interviews on this topic

Try answering out loud first, then open the model answer.

You've trained a model. How do you get it into production?

💬

First, save the model together with its preprocessing, as one pipeline, with a version number in a model registry. Then wrap it in an API, for example with FastAPI, with input validation. Package it in a Docker image and deploy it behind a load balancer, on Kubernetes or a managed service. Before full rollout, test it in shadow mode or as a canary on a small share of traffic. Then monitor latency, errors, input drift and the business metric, with an easy way to roll back to the previous version.

✅

  • Package model and preprocessing together, versioned
  • API with validation; containerise
  • Gradual rollout: shadow or canary
  • Monitoring and rollback

What is training serving skew, and how do you prevent it?

💬

It's when the data the model sees in production is computed differently from the data it was trained on, so the model quietly performs worse. For example, in training "average spend" was computed over 30 days in SQL, but the live service computes it over 7 days in Python. Prevention: use one shared feature pipeline or a feature store for both training and serving, log the features used at prediction time and compare them with training data, and add tests that run the same input through both paths.

✅

  • Definition and a concrete example
  • Cause: two different code paths for features
  • Fix: shared pipeline or feature store, logging, comparison tests

: Production ML maturity.

How does a feature store work, and what is a point-in-time (ASOF) join?

💬

A feature store defines a feature once and materialises it to two storage layers: an offline store (Parquet/Delta/warehouse) for large historical training sets, and an online key-value store (like Redis or DynamoDB) for single-digit-millisecond lookups during live inference. When building historical training data, a regular join on user_id leaks the future because it pulls today's feature values for an event that happened six months ago. A point-in-time or ASOF join matches each historical label at timestamp T with the latest feature value recorded at or before T, guaranteeing zero time-travel leakage.

✅

  • One feature definition → offline store (training batches) + online KV store (low-latency serving)
  • Eliminates training–serving skew across SQL and Python paths
  • Point-in-time (ASOF) join matches each label at T with features from <= T
  • For labeling: combine weak/LLM pre-labels with human verification and inter-annotator agreement

: High-signal question for AI Data Engineers, ML Engineers and MLOps Engineers.

What steps do you follow in a machine learning project, from start to finish?

💬

One, understand the problem and the success metric with the people who need it. Two, collect the data and explore it: size, missing values, distributions and obvious errors. Three, clean the data and create features. Four, split into training, validation and test sets. Five, train a simple baseline, then better models, comparing them on validation data. Six, evaluate the final model once on the test set and check its mistakes. Seven, deploy it, for example as an API or a Streamlit app. Eight, monitor it and retrain when data changes.

✅

  • Problem and metric first
  • Data exploration and cleaning
  • Baseline, then improvement on validation
  • Test once, deploy, monitor

Training creates the model. Inference serves it, fast, cheaply and reliably.
