🎛️ Fine-tuning and LoRA: specialising a model

EnglishHinglish

🏠 Real-life example

An MBBS doctor already knows general medicine. To become a cardiologist they don't redo school. They spend a few focused years on hearts. Fine-tuning is the same: take a model that already knows language and train it a little more on your specific task. LoRA is like learning cardiology from compact notes instead of rewriting every textbook.

💡 In simple words

Pre-training a large model from scratch costs millions. Fine-tuning starts from a pre-trained open model (Llama, Mistral, Qwen) and continues training on your examples, such as support tickets with ideal replies. Full fine-tuning updates every weight, which is expensive. LoRA and other PEFT (parameter-efficient fine-tuning) methods freeze the original weights and train small add-on matrices, so you can fine-tune on a single GPU. QLoRA also compresses (quantises) the base model. Always compare against prompting and RAG first, because they're cheaper and often enough.

🪜 Step by step

  1. First try prompting and RAG. Fine tune only if you need a consistent style, format or behaviour they can't give.
  2. Collect a few hundred to a few thousand high quality examples of input and ideal output.
  3. Choose a base model and use LoRA, so you train small adapter weights instead of the whole model.
  4. Train for a few epochs, watching validation loss to avoid overfitting.
  5. Evaluate against the base model on your eval set before using it. Keep the adapter versioned.

🔑 Key terms

Pre-trained model
A model already trained on huge general data.
LoRA / PEFT
Training small add-on weights instead of the whole model.
Quantisation
Storing weights with fewer bits to save memory.

👀 See it in action

python
from peft import LoraConfig, get_peft_model
config = LoraConfig(r=16, lora_alpha=32, target_modules=["q_proj", "v_proj"])
model = get_peft_model(base_model, config)
model.print_trainable_parameters()
# trainable: 0.1% of all parameters → fits on one GPU

Only a tiny fraction of the weights are trained.

⚠️ Common mistakes to avoid

  • Fine tuning to add facts. It's unreliable for knowledge; RAG is better for that.
  • Low quality or inconsistent training examples. The model copies your mistakes faithfully.

🙋 Questions learners ask

How much does fine tuning cost?

With LoRA on a small open model, it can run on a single GPU for a few hours. Hosted fine tuning APIs charge per training token.

What is QLoRA?

LoRA on a base model stored in 4 bit precision, which cuts memory so large models can be fine tuned on modest GPUs.

🎯 Asked in interviews on this topic

Try answering out loud first, then open the model answer.

When would you use prompting, RAG or fine tuning?

💬

I go in order of cost. First, prompting: clear instructions and examples solve many problems and take hours, not weeks. If the model needs knowledge it doesn't have, like our policies or recent data, I use RAG, because it's easy to update and gives citations. I'd fine tune when the problem is behaviour, not knowledge: a very specific output style or format, a narrow task done at huge volume where a small fine tuned model is cheaper and faster, or domain language the model handles poorly. Often the best system combines RAG with a lightly fine tuned model.

✅

  • Prompting first: fastest and cheapest
  • RAG for knowledge, especially changing or private data
  • Fine tuning for behaviour, format, cost at scale
  • They can be combined

: Judgement about cost and fit; asked for PMs too.

What is LoRA, and why is it popular?

💬

LoRA, low rank adaptation, fine tunes a big model by freezing the original weights and learning a small update for some weight matrices, written as the product of two thin matrices, A and B. Because the rank is small, you train maybe less than 1% of the parameters, which needs far less GPU memory and storage. You can keep one base model and swap small LoRA adapters for different tasks. QLoRA goes further by keeping the base model in 4 bit precision, so you can fine tune large models on a single GPU.

✅

  • Freeze base weights; learn low rank update A·B
  • Far fewer trainable parameters and memory
  • Swappable adapters per task
  • QLoRA: quantised base for even less memory

: Practical fine tuning knowledge.

Compare SFT, RLHF (PPO) and DPO for post-training an LLM. Why is the KL penalty needed?

💬

Supervised Fine-Tuning (SFT) teaches the base model to follow instructions by imitating curated (prompt, response) demos. RLHF goes further using human preference pairs (chosen vs rejected): it trains a separate reward model and uses PPO reinforcement learning to maximise reward while keeping a KL-divergence penalty so the policy doesn't drift too far from the SFT reference and 'reward-hack' with gibberish or sycophancy. Direct Preference Optimization (DPO) mathematically rewrites that reward + KL objective into a simple binary cross-entropy loss directly on the preference pairs, eliminating the separate reward model and unstable PPO loop. For verifiable tasks like math or code, GRPO/RLVR trains reasoning chains against unit-test rewards.

✅

  • SFT imitates demos; RLHF/DPO align using (prompt, chosen, rejected) preference pairs
  • KL-divergence penalty stops the model from drifting and reward-hacking
  • DPO optimises preferences directly with cross-entropy without a separate reward model
  • RLVR / GRPO uses verifiable code or math rewards for reasoning models

: Core 2026 post-training and alignment question for Research, ML and Agent engineers.

📌 Remember

Prompting → RAG → fine-tuning, in that order of cost.
