⚡ Cost and latency: caching, model routing and token budgets

EnglishHinglish

🏠 Real-life example

A busy dabbawala doesn't send a senior manager to deliver every lunch box, and doesn't cook a fresh meal when the same order was just made. Simple deliveries go to the quickest person, repeated orders are served from what's ready, and only special requests get extra effort. Good AI products do the same with models: small fast model for easy tasks, cached answers for repeats, the big model only when needed.

💡 In simple words

Every AI feature has a cost per request (input tokens plus output tokens times the model's price) and a latency (time to first token, then total time). Measure both per feature from day one: p50 and p95 latency, cost per request and cost per active user. Main levers: (1) Model routing: send simple tasks such as classification or short rewrites to a small, cheap model and only hard tasks to the large one; check quality with your evals before switching. (2) Prompt caching: providers can cache a long, unchanging prefix (system prompt, tool definitions, a big document) so repeat calls are cheaper and faster; keep that prefix identical and first. (3) Response or semantic caching: return a saved answer when the same, or a very similar, question was answered recently, but include the user or tenant in the cache key so one person never sees another's answer, and expire entries when data changes. (4) Fewer tokens: shorter prompts, fewer retrieved chunks after reranking, and limits on output length. (5) Perceived speed: stream, run retrieval and other calls in parallel, and show progress. (6) Batch or background work for anything not needed right now, often at a lower price.

🎬 See how it works

Check the cache first (with the user in the key). On a miss, a router sends easy requests to a small, cheap model and hard ones to the large model. Log cost and latency for every call.

🪜 Step by step

  1. Log tokens, cost and latency (time to first token and total) for every call, tagged by feature, model and prompt version.
  2. Build a dashboard of cost per request, cost per active user and p50/p95 latency per feature, with a monthly budget alert.
  3. Find the biggest spender and try a smaller model for it; keep the switch only if your evals stay within the agreed limit.
  4. Make the long prompt prefix identical across calls and enable prompt caching; measure the cache hit rate.
  5. Add a response cache for repeated questions with identity in the key and a sensible expiry.
  6. Cut tokens: shorter instructions, fewer reranked chunks, max output tokens; then stream and parallelise the remaining steps.

🔑 Key terms

Model routing
Choosing a small or large model per request based on how hard the task is.
Prompt caching
The provider reuses a long, unchanged prompt prefix so repeat calls cost less and start faster.
Semantic cache
Returning a saved answer for a question that means the same as a recent one.
p95 latency
The time within which 95% of requests finish; it shows the slow experience users complain about.

👀 See it in action

python
def answer(user, question):
    key = f"{user.tenant}:{normalise(question)}"        # tenant in the key: no cross-user leaks
    if (hit := cache.get(key)):
        return hit                                       # ~5 ms, ₹0
    model = "small" if classify_difficulty(question) == "easy" else "large"
    res = llm.generate(
        model=model,
        system=[{"text": LONG_POLICY_PROMPT, "cache": True}],  # same prefix every time → prompt cache
        messages=[{"role": "user", "content": question}],
        max_tokens=400,
    )
    metrics.record(model=model, cost=res.cost, ms=res.latency_ms)
    cache.set(key, res.text, ttl=3600)
    return res.text

Check the cache first, route by difficulty, keep the long prefix cacheable, cap output, and record cost and latency.

⚠️ Common mistakes to avoid

  • Using the biggest model for every step, including simple classification, "just to be safe".
  • A cache key without user or tenant identity, which can leak one customer's answer to another.
  • Optimising average latency while p95 users wait 12 seconds. Users remember the slow cases.

✅ Quick check

You add a response cache to an internal HR assistant. What must the cache key include?

  1. The user's or tenant's identity and permissions, plus the normalised question
  2. Only the question text, so more requests hit the cache
  3. The time of day, so answers refresh hourly
Show answer

A. The user's or tenant's identity and permissions, plus the normalised question: Without identity in the key, an answer built from one person's private data can be served to someone else. That's a data leak, not a speed win.

🙋 Questions learners ask

How do I estimate cost before building?

Multiply expected requests per day by average input and output tokens and the model prices, then add 30% for retries and growth. Compare it with the value per task.

Does streaming reduce cost?

No, it reduces perceived latency: users see words sooner, but the same tokens are generated. It does let users stop early, which can save some tokens.

🎯 Asked in interviews on this topic

Try answering out loud first, then open the model answer.

Your AI feature costs too much per user. Walk me through how you would reduce cost without hurting quality.

💬

First I measure: cost per request and per active user by feature, model and prompt version, so I know where the money goes. Then I work through the levers in order of risk. I route simple steps, like classification or query rewriting, to a smaller model and keep the switch only if my evals stay within an agreed limit. I make the long system prompt prefix identical across calls and turn on prompt caching. I add a response cache for repeated questions, with the user or tenant in the cache key so nobody sees someone else's answer. I cut tokens with shorter instructions, fewer chunks after reranking and a max output length. Anything not needed right away moves to batch processing. I report the before and after cost together with the quality scores.

✅

  • Measure cost by feature, model and version first
  • Route easy steps to small models, checked by evals
  • Prompt caching with a stable prefix
  • Response cache with identity in the key
  • Fewer tokens and batch where possible; show before and after with quality

Measure cost and p95 per feature; route easy tasks to small models, cache safely with identity in the key, cut tokens, stream and parallelise.
