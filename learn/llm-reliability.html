🛟 Reliability: timeouts, retries, fallbacks and rate limits

EnglishHinglish

🏠 Real-life example

When your usual auto driver doesn't pick up, you don't wait at the gate for an hour. You wait a little, call once more, then book a cab, and if all else fails you take the bus. A reliable AI feature has the same plan: a time limit, a sensible retry, a backup model and a useful screen when nothing works.

💡 In simple words

Model APIs fail in normal ways: rate limits (HTTP 429), overloaded servers (5xx), slow responses and occasional outages. Plan for each. Set a timeout on every call, shorter for interactive features. Retry only errors that may pass (429, 5xx, timeouts) with exponential backoff and jitter, at most two or three times, and respect the Retry-After header; never retry a 400 bad request unchanged. Make actions idempotent so a retry can't send two emails or two refunds: use an idempotency key. Keep a fallback chain: another model or provider for the same task, then a cached or simpler answer, then a clear message with a non-AI path (a template, a search box, "talk to a human"). Put your own rate limits and per-user budgets in front of the model so one user or a bug can't burn your quota. Use a circuit breaker: if a provider keeps failing, stop calling it for a minute and use the fallback. Track error rate, retries and fallback rate on a dashboard with alerts, and test the failure paths on purpose.

🎬 See how it works

A call times out or gets a 503. The app retries with growing waits, then the circuit breaker switches to a backup model, and if that fails too, users get a helpful non-AI path.

🪜 Step by step

  1. Set a timeout on every model and tool call, shorter for interactive screens than for background jobs.
  2. Retry only temporary errors (429, 5xx, timeouts) with exponential backoff, jitter and a cap of two or three tries; honour Retry-After.
  3. Give every action that changes something (email, refund, ticket) an idempotency key so retries can't repeat it.
  4. Define the fallback chain per feature: backup model, cached or simpler answer, then a non-AI path with a clear message.
  5. Add per-user rate limits and daily budgets in front of the model, plus a circuit breaker per provider.
  6. Alert on error rate, fallback rate and budget, and test failures on purpose (block the provider in staging and watch what users see).

🔑 Key terms

Exponential backoff
Waiting longer after each failed try (1 s, 2 s, 4 s), with a little randomness (jitter).
Fallback chain
The ordered backup plan: another model, a cached or simple answer, then a non-AI path.
Circuit breaker
Stops calling a failing service for a while so the app stays fast and recovers.
Idempotency key
A unique ID per action so a retried request isn't carried out twice.

👀 See it in action

python
RETRYABLE = {429, 500, 502, 503, 504}

def generate_with_fallback(prompt):
    for provider in [primary, backup]:                 # fallback chain
        if breaker.is_open(provider):
            continue                                   # skip a provider that keeps failing
        for attempt in range(3):
            try:
                return provider.generate(prompt, timeout=8)
            except ApiError as e:
                if e.status not in RETRYABLE:
                    raise                              # a 400 won't fix itself
                time.sleep(e.retry_after or (2 ** attempt + random.random()))
            except Timeout:
                pass
        breaker.record_failure(provider)
    return SAFE_FALLBACK_MESSAGE                       # template + "talk to a human"

Timeout every call, retry only what can pass with backoff, skip broken providers, and always end with a useful fallback.

⚠️ Common mistakes to avoid

  • Retrying immediately in a tight loop during a rate limit, which makes the overload worse and gets you blocked longer.
  • Retrying an agent step that already sent an email, so the customer gets it twice.
  • A blank screen or raw stack trace when the model is down, instead of a useful fallback.

✅ Quick check

Your model call fails with HTTP 400 (bad request). What should your code do?

  1. Don't retry; log it, fix or validate the request, and show a fallback
  2. Switch to the backup provider and send the same request
  3. Retry it five times with backoff
Show answer

A. Don't retry; log it, fix or validate the request, and show a fallback: A 400 means the request itself is wrong, so repeating it fails every time and wastes money. Retries are for temporary errors such as 429, 5xx and timeouts.

🙋 Questions learners ask

Should I use two model providers?

For important features, yes: keep a tested backup model and run your evals on it too, because prompts don't always transfer perfectly between models.

What is a good timeout for an AI feature?

Base it on the user's patience and your p99: often 10 to 20 seconds for a streaming answer (with first token expected within 2 to 3 seconds) and longer for background jobs.

🎯 Asked in interviews on this topic

Try answering out loud first, then open the model answer.

The model provider has an outage during your peak hour. How should your AI feature behave, and how do you build that?

💬

Users should still get something useful and nothing should break or repeat. Every call has a timeout. I retry only temporary errors, 429s, 5xx and timeouts, with exponential backoff, jitter and a small cap, and I respect Retry-After. A circuit breaker stops calling a provider that keeps failing, and a fallback chain takes over: a tested backup model, then a cached or simpler answer, then a clear message with a non-AI path like a template or talking to a human. Actions that change things carry an idempotency key so retries can't send two refunds. I also have per-user rate limits, alerts on error and fallback rates, and I test the outage path in staging on purpose.

✅

  • Timeouts on every call
  • Retry only temporary errors with backoff and a cap
  • Circuit breaker plus a fallback chain ending in a non-AI path
  • Idempotency keys for actions
  • Alerts and deliberate failure testing

: Production maturity: designing for failure, not just the happy path.

📌 Remember

Timeouts, retries only for temporary errors, idempotent actions, a fallback chain and your own rate limits.
