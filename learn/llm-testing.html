🧪 Testing AI features in code: mocks, recorded responses and contract tests

EnglishHinglish

🏠 Real-life example

A driving school tests the car's brakes, lights and indicators every time, the same way, before checking how well a student drives on real roads. Ordinary tests are the brake check: fast and repeatable. Evals are the road test: they judge the quality of the driving. A good AI product needs both.

💡 In simple words

Model answers vary, but most of the code around the model is ordinary code that should be tested like any other: building prompts, parsing and validating outputs, choosing tools, retries and fallbacks, permission checks and UI states. Use a few layers. Unit tests replace the model with a fake that returns fixed responses, including bad ones (invalid JSON, an empty answer, a timeout, a 429), so you can check your code handles each case; they are fast and free. Recorded response tests save real model responses once (fixtures) and replay them, so a test of the full flow runs without calling the API each time; re-record them when you change the prompt or model. Contract tests check that outputs match your schema and that your prompt builder never leaks other users' data. A small number of live smoke tests call the real model on a schedule to catch provider changes. Evals sit on top and judge quality. Keep the default test run fast and offline; never let a flaky live call block every pull request.

🎬 See how it works

A testing pyramid for AI features: many fast unit tests with a fake model, some replayed recorded responses, a few scheduled live smoke tests, and evals judging quality on the side.

🪜 Step by step

  1. Wrap every model call in one function so tests can replace it with a fake.
  2. Write unit tests with a fake model for the happy path and for bad cases: invalid JSON, empty text, a timeout, a 429.
  3. Record a few real responses as fixtures and replay them in end to end tests; re-record when the prompt or model changes.
  4. Add contract tests: outputs match the schema, prompts include only the current user's data, tools get validated arguments.
  5. Run a small live smoke test on a schedule, separate from pull requests, and alert if it fails.
  6. Keep evals as a separate job that judges quality, and link both in your CI checklist.

🔑 Key terms

Fake / mock model
A stand-in that returns fixed responses so tests are fast, free and repeatable.
Fixture (recorded response)
A saved real model response replayed in tests instead of calling the API.
Contract test
A test that checks outputs and inputs follow an agreed schema or rule.
Smoke test
A small live check, often scheduled, that the real integration still works.

👀 See it in action

typescript
import { test, expect, vi } from "vitest";
import { classifyTicket } from "../lib/classify";
import * as ai from "../lib/ai";

test("invalid JSON from the model → one retry, then 'other'", async () => {
  const call = vi.spyOn(ai, "callModel")
    .mockResolvedValueOnce({ text: "Sure! The category is billing" })  // not JSON
    .mockResolvedValueOnce({ text: "{oops" });                          // still bad
  const res = await classifyTicket("Refund not received");
  expect(call).toHaveBeenCalledTimes(2);       // retried once
  expect(res.category).toBe("other");          // safe fallback, no crash
});

test("prompt never includes another tenant's documents", async () => {
  const prompt = await buildPrompt({ tenant: "acme", question: "leave policy" });
  expect(prompt).not.toContain("globex");
});

A fake model lets you test the unhappy paths (bad JSON, retries, fallbacks) and data isolation in milliseconds.

⚠️ Common mistakes to avoid

  • Calling the real model in every unit test, making CI slow, costly and randomly red.
  • Only testing the happy path, so the first malformed response crashes production.
  • Treating evals and tests as the same thing; you need both.

Show answer

A. Use a fake model and recorded responses so tests are fast and repeatable; run a few live smoke tests on a schedule: Live calls make every test slow, costly and flaky. Fakes and fixtures test your code's logic reliably, smoke tests watch the real integration, and evals judge quality.

🙋 Questions learners ask

How do I test something whose output changes every time?

Test the parts that shouldn't change: your code's logic with fake responses, the shape of outputs with schemas, and required facts with simple checks. Judge the wording with evals.

Should temperature be 0 in tests?

For live smoke tests, a low temperature reduces variation but doesn't remove it completely. That's why the main test suite uses fakes and fixtures instead.

🎯 Asked in interviews on this topic

Try answering out loud first, then open the model answer.

How do you write automated tests for code that calls an LLM?

💬

I separate code correctness from answer quality. All model calls go through one function, so in unit tests I replace it with a fake that returns fixed responses, including bad ones such as invalid JSON, an empty answer, a timeout or a 429, and check my parsing, retries and fallbacks. For end to end flows I replay recorded real responses as fixtures, and re-record them when the prompt or model changes. Contract tests check that outputs match the schema and that prompts only contain the current user's data. A small live smoke test runs on a schedule to catch provider changes. Answer quality is judged separately by the eval suite. The pull request suite stays fast, free and deterministic.

✅

  • Fake model for unit tests, including failure cases
  • Recorded responses for end to end flows
  • Contract tests for schemas and data isolation
  • Scheduled live smoke tests
  • Evals for quality, kept separate from tests

: Engineering discipline around non-deterministic systems.

📌 Remember

Test the code around the model with fakes and fixtures, check contracts and data isolation, add scheduled smoke tests, and let evals judge quality.
