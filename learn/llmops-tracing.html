📡 LLMOps: tracing, model routing, caching and cutting cost & latency

EnglishHinglish

🏠 Real-life example

Think of a hospital triage desk and a courier tracking number. Not every patient with a mild cold needs a top neurosurgeon: the triage nurse routes simple cases to a general doctor and complex ones to a specialist. That's model routing. And when a parcel is delayed, the tracking number shows every hub it passed through and where it got stuck. That's LLM tracing.

💡 In simple words

In production, a single user question might trigger query rewriting, embedding search, reranking, two tool calls, and a final LLM answer. Without tracing (OpenTelemetry, Langfuse, Arize Phoenix), you cannot tell which step was slow or why an answer went wrong. A trace records every nested span with its prompt version, inputs, outputs, token count, cost and latency. To cut latency and cost by 50–80%: (1) stream tokens so Time to First Token (TTFT) is under 500 ms, (2) use prompt/prefix caching for long system prompts and few-shot examples, (3) add semantic caching for repeated common questions, and (4) use an LLM gateway with model routing — sending simple classification/extraction to a fast, cheap small model and reserving frontier models for hard reasoning.

🪜 Step by step

  1. Instrument every LLM call, retrieval query and tool execution with a trace ID and child spans (recording prompt version, model, tokens, cost and latency).
  2. Measure Time to First Token (TTFT) and tokens-per-second separately from end-to-end latency, and stream responses to the UI.
  3. Place static instructions, tool definitions and few-shot examples at the start of every prompt so provider prefix caching cuts input token cost and TTFT by 50–80%.
  4. Put an LLM gateway in front of providers to handle rate limits, automatic retries, fallback models (e.g. Claude → GPT or primary region → backup region) and per-team cost budgets.
  5. Route requests by complexity: use a small fast model (or classifier) for simple intents and extraction, and escalate only hard queries to a frontier model.

🔑 Key terms

Trace & spans
A full record of one user request (the trace) broken into each LLM, retrieval and tool step (spans) with latency and tokens.
Prompt / prefix caching
Reusing the precomputed KV cache of a shared static prefix (system prompt + examples) across requests to cut cost and TTFT.
Model routing / cascading
Sending simple queries to a small cheap model and escalating only hard queries to a large frontier model.

Tracing pinpoints latency per step, and routing + prefix caching keep both TTFT and cost tiny.

⚠️ Common mistakes to avoid

  • Putting a dynamic timestamp or user ID in the very first line of the system prompt, which invalidates prefix caching on every single request!
  • Using semantic caching without scoping by tenant_id or user permissions, accidentally serving one customer's cached answer to another customer.

✅ Quick check

To benefit from provider prompt/prefix caching, where should your static system instructions and few-shot examples be placed in the prompt?

  1. Shuffled randomly on every request
  2. At the very beginning (a byte-identical prefix), with dynamic user content placed at the end
  3. At the very end, after the user's dynamic question
Show answer

B. At the very beginning (a byte-identical prefix), with dynamic user content placed at the end: KV-cache reuse only works up to the first token that changes, so static instructions must form the leading prefix.

🙋 Questions learners ask

What is the difference between prefix caching and semantic caching?

Prefix caching reuses the GPU KV-cache of the exact shared prompt prefix and still generates a fresh answer. Semantic caching embeds the user's question and, if a nearly identical question was just answered, returns the saved answer directly without calling the LLM.

How do you debug a sudden 2× spike in LLM latency?

Check your trace spans by p95 duration: did retrieval/reranking slow down, did a prompt change double the output token count, or is the model provider's TTFT degraded (triggering your fallback)?

🎯 Asked in interviews on this topic

Try answering out loud first, then open the model answer.

Your LLM feature is too slow and too expensive. What do you do?

💬

First I measure where tokens and time go: prompt size, output size, number of calls. Then the main levers: stream the response so users see text immediately; shorten prompts and retrieved context; cache answers to repeated questions and use prompt caching for long fixed system prompts; route easy requests to a smaller, cheaper model and only hard ones to the big model; reduce agent steps; and batch background jobs. After each change, I rerun evals, so I know quality didn't drop.

✅

  • Measure first: tokens, calls, time per step
  • Streaming for perceived latency
  • Shorter context, caching, smaller models via routing, fewer steps
  • Check quality with evals after each change

: Cost and latency trade offs are a top 2026 theme.

What's different about operating LLM applications compared with classic ML models?

💬

Several new things to manage. Prompts are code, so they need versioning, review and testing. Evaluation suites must run on every prompt or model change, because there's no single accuracy number. Cost has to be monitored per request and per feature, since it scales with tokens. Providers update models, so I pin versions and re run evals before upgrading. Logging and tracing every step of a chain or agent is essential for debugging. And there are safety checks: prompt injection, PII in logs, and content filters.

✅

  • Prompt versioning and testing
  • Eval suites as release gates
  • Token cost monitoring
  • Model version pinning, tracing, safety controls

How do distributed tracing, prompt caching, semantic caching and model routing work together in an LLM gateway?

💬

Every user request gets a trace ID and child spans for query rewriting, retrieval, reranking, LLM calls and tool calls, recording exact inputs, outputs, latency, token counts and cost. In the gateway, prompt/prefix caching reuses the KV cache of static system instructions and few-shot examples across requests, cutting input token cost by 50–90%. Semantic caching embeds the query and returns a vetted cached response for high-similarity repeat FAQs (scoped by tenant and permissions). Finally, a model router sends 70–80% of simple classification or FAQ queries to a fast, cheap small model and only escalates complex reasoning to a frontier model, with automatic fallback if a provider returns 429 or 503.

✅

  • Trace + child spans capture latency, tokens, cost and prompt version at every step
  • Prompt/prefix caching reuses KV cache for static system prompts and examples
  • Semantic caching serves repeat FAQs (strictly scoped by tenant/permissions and freshness)
  • Model routing sends simple traffic to small models + automatic provider fallbacks

: Core 2026 LLMOps and AI Platform architecture question.

Design a platform to serve an LLM to 1,000 requests per second.

💬

Clarify model size, prompt and output lengths, and latency targets, especially time to first token. Requests go through a gateway with authentication, rate limits per customer and routing. Behind it, a pool of GPU servers running an inference engine like vLLM with continuous batching and paged KV cache, autoscaled on queue depth. Add a prefix and response cache for repeated prompts, and route simple requests to a smaller model. Estimate capacity from tokens per second per GPU, plan headroom for peaks, and spread across zones. Monitor time to first token, tokens per second, queue time, errors and cost per thousand tokens, and roll out new model versions with canaries.

✅

  • Clarify sizes and latency targets
  • Gateway: auth, rate limits, routing
  • Inference engine with batching, autoscaling on queue
  • Caching, model routing, capacity planning, monitoring, canaries

Your AI feature's response time doubled since yesterday. How do you investigate?

💬

Check what changed: deploys, prompt changes, a model version change, or a provider status issue. Then look at traces to find which step got slower: retrieval, the LLM call, a tool call or our own code. If it's the LLM call, see whether prompts or outputs got longer, for example a bigger retrieved context or a prompt change that makes answers longer, or whether the provider's latency rose. If it's ours, check database queries, cache hit rate and traffic volume. Fix the cause, roll back if needed, and add a latency alert per step so we catch it sooner next time.

✅

  • What changed? deploys, prompts, models, provider
  • Use per step traces to localise
  • Token count changes are a common cause
  • Fix or roll back; add per step alerts

Trace every span, put static instructions first for prefix caching, route easy tasks to small models, and always configure a fallback.
