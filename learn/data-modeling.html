🏗️ Data modelling: designing tables for analysis

EnglishHinglish

🏠 Real-life example

A supermarket bill lists what happened: items, quantities, amounts. That's a 'fact'. Separately, the store keeps details about products (brand, category) and stores (city, size). Those are 'dimensions'. Keeping the bills slim and the details in their own tables makes every report faster and cleaner.

💡 In simple words

Analytics databases (data warehouses like BigQuery or Snowflake) are designed differently from app databases. The classic design is a star schema: a central fact table of events (sales, clicks, trips) with numeric measures, surrounded by dimension tables that describe the who, what, where and when. Window functions such as running totals, ranks and 'previous value' let you analyse sequences without messy self-joins. A good model makes common questions easy and wrong answers hard.

🪜 Step by step

  1. Decide the grain: what does one row mean? One order, one order line, or one customer per day?
  2. Create a fact table for events and numbers (order_id, date_id, product_id, quantity, amount).
  3. Create dimension tables for descriptions (product name and category, customer city, calendar dates).
  4. Connect them with keys in a star shape: facts in the middle, dimensions around.
  5. Document each table and column, and add tests (unique keys, no NULLs where not allowed).

🔑 Key terms

Fact table
Events with numbers, e.g. each sale and its amount.
Dimension table
Descriptive details, e.g. product name or store city.
Window function
A calculation across related rows, such as a rank or running total.

👀 See it in action

sql
SELECT store_id, sale_date, amount,
       SUM(amount) OVER (PARTITION BY store_id ORDER BY sale_date) AS running_total
FROM fact_sales;

A running total per store, with no self-join needed.

⚠️ Common mistakes to avoid

  • Mixing grains in one table, like daily totals and individual orders together. Sums become wrong.
  • Overwriting history: if a customer moves city and you overwrite it, old sales get the new city. Keep history where it matters.

✅ Quick check

In a star schema, where does the 'product category' column belong?

  1. Repeated in every table
  2. The fact table
  3. A product dimension table
Show answer

C. A product dimension table: Category describes the product, so it lives in the product dimension, which the fact table links to.

🙋 Questions learners ask

Normalised tables or a star schema?

Apps use normalised tables to avoid duplicate data while writing. Analytics uses star schemas because they make reading and reporting simple and fast.

Why does data modelling matter for AI?

Clean, well defined tables make features and training data trustworthy. Many 'model problems' are really data definition problems.

🎯 Asked in interviews on this topic

Try answering out loud first, then open the model answer.

Why use Parquet and partitioning in a data lake?

💬

Parquet is a columnar file format: it stores each column together and compresses it well. Analytics queries usually read a few columns, so Parquet reads much less data than CSV, and it also keeps schema and types. Partitioning splits data into folders by a column like date, so a query for last week only reads those folders, which is called partition pruning. I'd pick partition columns that queries filter on and avoid too many tiny files, which slow everything down, by compacting them regularly.

✅

  • Columnar, compressed, typed
  • Partition pruning on common filters
  • Avoid over partitioning and small files

What is a slowly changing dimension, type 2?

💬

Dimensions like customer address change over time. Type 1 just overwrites the old value, so history is lost. Type 2 keeps history: when something changes, we close the old row by setting an end date and is_current = false, and insert a new row with the new value, a new start date and is_current = true. That way, a sale from last year joins to the address the customer had then. It's important for correct historical reports and for building training data that reflects what was known at the time.

✅

  • Type 1 overwrites; type 2 keeps history
  • Start and end dates plus a current flag
  • Enables correct point in time joins, including for ML training data

Explain fact and dimension tables in a star schema.

💬

A fact table stores events or measurements, like each order with quantity and amount, plus keys to dimensions. Dimension tables store descriptive context, like customer, product, date and store. It's called a star because the fact table sits in the middle with dimensions around it. This makes analytics queries simple and fast: "total sales by product category by month" is a join from the fact to two dimensions and a group by. Getting the grain right, meaning what one row in the fact table represents, is the most important design decision.

✅

  • Facts = events and measures; dimensions = descriptive context
  • Star layout simplifies analytics
  • Define the grain first

Design the data pipeline that feeds daily sales analytics and an ML demand forecast.

💬

Sources: order database via change data capture, product catalogue, and store data. Land raw data in a lake or warehouse partitioned by date. Transform with dbt into clean staging tables, then a star schema with an orders fact table and product, store and date dimensions. The ML team reads a feature table built from the same models, so analytics and ML agree. Orchestrate with Airflow, each task idempotent by date, with data quality tests between layers, and alerts if data is late or wrong. Backfills are reruns of date partitions. Document lineage and owners, so people know where numbers come from.

✅

  • Sources and ingestion (CDC)
  • Raw → staging → modelled layers (star schema)
  • Shared feature tables for ML
  • Orchestration, idempotency, quality tests, backfills, lineage
