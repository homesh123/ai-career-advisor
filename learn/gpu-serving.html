⚡ Serving LLMs efficiently: GPUs, batching and cost

EnglishHinglish

🏠 Real-life example

An auto-rickshaw carrying one passenger at a time is slow and expensive per person. A bus that waits a few seconds to fill up moves far more people for the same fuel. LLM servers 'batch' many user requests together on one GPU for the same reason: much better throughput and lower cost per request.

💡 In simple words

Self-hosting open models (Llama, Qwen, Mistral) needs GPUs, and GPUs are expensive. Inference servers like vLLM or TGI maximise GPU use with continuous batching (adding new requests mid-flight) and efficient memory for the conversation cache. Key metrics: time to first token (how fast the reply starts), tokens per second, p95 latency and cost per 1,000 requests. Quantisation shrinks models to fit cheaper GPUs, caching repeated prompts saves money, and an LLM gateway in front routes traffic, enforces budgets and falls back between providers.

🪜 Step by step

  1. Pick the smallest model that meets your quality bar on your eval set.
  2. Consider quantisation (8 bit or 4 bit) to fit on cheaper GPUs with little quality loss; measure it.
  3. Serve with an LLM inference engine (vLLM, TGI) for continuous batching and efficient KV cache memory.
  4. Measure time to first token, tokens per second and cost per 1,000 requests under realistic load.
  5. Autoscale on queue length, cache repeated prompts, and route easy requests to smaller models.

🔑 Key terms

Batching
Processing many requests together to use the GPU fully.
Time to first token
How quickly the first words of a reply appear.
p95 latency
95% of requests are faster than this. It captures the slow tail.

👀 See it in action

bash
pip install vllm
vllm serve Qwen/Qwen2.5-7B-Instruct --max-model-len 8192
# → OpenAI-compatible API on :8000 with continuous batching built in

# Track: time-to-first-token, tokens/sec, p95 latency, GPU utilisation, ₹ per 1k requests

One command gives you a batched, production-style LLM server.

⚠️ Common mistakes to avoid

  • Comparing GPUs only by price per hour. Compare cost per request at your real traffic.
  • Self hosting by default. At low volume, an API is often cheaper and far simpler.

🙋 Questions learners ask

What is batching and why does it help?

Processing many requests together keeps the GPU busy. Continuous batching adds new requests into a running batch instead of waiting.

When should we self host an LLM?

When data can't leave your environment, when volume is high enough that it's cheaper, or when you need a fine tuned open model.

🎯 Asked in interviews on this topic

Try answering out loud first, then open the model answer.

Your LLM feature is too slow and too expensive. What do you do?

💬

First I measure where tokens and time go: prompt size, output size, number of calls. Then the main levers: stream the response so users see text immediately; shorten prompts and retrieved context; cache answers to repeated questions and use prompt caching for long fixed system prompts; route easy requests to a smaller, cheaper model and only hard ones to the big model; reduce agent steps; and batch background jobs. After each change, I rerun evals, so I know quality didn't drop.

✅

  • Measure first: tokens, calls, time per step
  • Streaming for perceived latency
  • Shorter context, caching, smaller models via routing, fewer steps
  • Check quality with evals after each change

: Cost and latency trade offs are a top 2026 theme.

What's the computational cost of self attention, and how can it be reduced?

💬

For a sequence of n tokens with dimension d, attention compares every token with every other token, so time is roughly O(n² · d) and the attention matrix needs O(n²) memory. That's why long contexts are expensive. Approaches to reduce it include FlashAttention, which computes exact attention in tiles to save memory and is much faster on GPUs; sparse or sliding window attention, which only looks at nearby tokens; linear attention approximations; and at inference, the KV cache plus grouped query attention to reduce memory per token.

✅

  • O(n²) in sequence length
  • FlashAttention: exact, memory efficient, IO aware
  • Sparse or windowed attention, linear approximations
  • Inference tricks: KV cache, GQA

: Depth on efficiency, which labs care about.

What is the KV cache in LLM inference?

💬

When an LLM generates text one token at a time, each new token needs attention over all previous tokens. Without a cache, we'd recompute the keys and values of every previous token at every step, which is wasteful. The KV cache stores the keys and values computed so far, so each step only computes them for the new token. That makes generation much faster, but the cache uses a lot of GPU memory, growing with sequence length and batch size, which is why techniques like grouped query attention and paged attention, as in vLLM, matter.

✅

  • Stores past keys and values during generation
  • Avoids recomputation; big speedup
  • Costs GPU memory; grows with length and batch
  • GQA and paged attention manage that memory

: Inference fundamentals, asked by labs and LLM infra teams.

How does post-training quantisation (INT8/INT4, AWQ, GPTQ) work, and why do activation outliers break naive INT4?

💬

Quantisation maps 16-bit floating-point weights (FP16/BF16) onto a narrow grid of 8-bit or 4-bit integers using a scale factor, cutting GPU memory by 2× to 4× and speeding up memory-bandwidth-bound token generation. Naive round-to-nearest INT4 degrades accuracy because transformer activations above ~6B parameters develop huge outlier channels (100× larger than normal); stretching 16 integer buckets across that range squashes all normal weights to zero. AWQ and GPTQ fix this using a small calibration set: AWQ scales up the 1% of weight channels that multiply large activation outliers before quantising, preserving accuracy.

✅

  • Maps FP16/BF16 weights to INT8/INT4 grids; cuts VRAM 2–4× and speeds up token decoding
  • Transformer activation outliers stretch the quantisation grid and crush normal values
  • AWQ / GPTQ use calibration data to protect salient weight channels
  • Also quantise the KV cache (FP8/INT8) for long contexts and big batch sizes

: Tests deep understanding of LLM efficiency and quantisation.

How do you serve an open source LLM efficiently on GPUs?

💬

Use an inference server built for LLMs, like vLLM or TGI, rather than a plain web server. They provide continuous batching, which adds new requests into the running batch so the GPU stays busy, and paged attention to manage KV cache memory. Choose the smallest model that meets quality, and consider quantisation, like 8 bit or 4 bit, to fit on cheaper GPUs. Then autoscale on queue length or tokens per second, set max token limits, and monitor time to first token, tokens per second, GPU memory and cost per request.

✅

  • LLM inference server (vLLM, TGI)
  • Continuous batching, paged KV cache
  • Right sized and quantised models
  • Autoscale and monitor latency, throughput, cost

: LLM infrastructure is now part of most MLOps interviews.

How do distributed tracing, prompt caching, semantic caching and model routing work together in an LLM gateway?

💬

Every user request gets a trace ID and child spans for query rewriting, retrieval, reranking, LLM calls and tool calls, recording exact inputs, outputs, latency, token counts and cost. In the gateway, prompt/prefix caching reuses the KV cache of static system instructions and few-shot examples across requests, cutting input token cost by 50–90%. Semantic caching embeds the query and returns a vetted cached response for high-similarity repeat FAQs (scoped by tenant and permissions). Finally, a model router sends 70–80% of simple classification or FAQ queries to a fast, cheap small model and only escalates complex reasoning to a frontier model, with automatic fallback if a provider returns 429 or 503.

✅

  • Trace + child spans capture latency, tokens, cost and prompt version at every step
  • Prompt/prefix caching reuses KV cache for static system prompts and examples
  • Semantic caching serves repeat FAQs (strictly scoped by tenant/permissions and freshness)
  • Model routing sends simple traffic to small models + automatic provider fallbacks

: Core 2026 LLMOps and AI Platform architecture question.

Design a platform to serve an LLM to 1,000 requests per second.

💬

Clarify model size, prompt and output lengths, and latency targets, especially time to first token. Requests go through a gateway with authentication, rate limits per customer and routing. Behind it, a pool of GPU servers running an inference engine like vLLM with continuous batching and paged KV cache, autoscaled on queue depth. Add a prefix and response cache for repeated prompts, and route simple requests to a smaller model. Estimate capacity from tokens per second per GPU, plan headroom for peaks, and spread across zones. Monitor time to first token, tokens per second, queue time, errors and cost per thousand tokens, and roll out new model versions with canaries.

✅

  • Clarify sizes and latency targets
  • Gateway: auth, rate limits, routing
  • Inference engine with batching, autoscaling on queue
  • Caching, model routing, capacity planning, monitoring, canaries
