📚 RAG: letting an LLM answer from your documents

EnglishHinglish

🏠 Real-life example

An open-book exam: you don't memorise the whole textbook. When a question comes, you find the right pages, read them, and write your answer from them, citing the chapter. RAG (Retrieval-Augmented Generation) makes an LLM take an open-book exam with your company's documents.

💡 In simple words

There are two phases. Indexing: split documents into chunks (a few paragraphs each), create an embedding for each chunk, and store them in a vector database. Answering: embed the user's question, retrieve the most relevant chunks, put them into the prompt ('Answer only from these sources…'), and let the LLM write the answer with citations. RAG keeps answers current and grounded in your data without retraining the model. Most RAG quality problems are retrieval problems, such as bad chunking or missing documents, so measure retrieval separately from the final answer.

🎬 See how it works

Indexing happens once: documents → chunks → embeddings → vector DB. For each question, retrieve the best chunks, add them to the prompt, and answer with the source.

🪜 Step by step

  1. Collect and clean the documents: remove duplicates, old versions and junk text.
  2. Chunk them along headings and paragraphs, a few hundred tokens each, and keep title, section and date as metadata.
  3. Embed the chunks and store them; for each question, retrieve the top matches (ideally hybrid search plus a reranker).
  4. Prompt: "Answer only from the sources below and cite them. If they don't contain the answer, say so."
  5. Build an eval set of real questions; measure retrieval (was the right chunk found?) and answers (correct and faithful?) separately.

🔑 Key terms

Chunking
Splitting documents into small, searchable pieces.
Retrieval
Finding the most relevant chunks for a question.
Grounding / citations
Answering only from the retrieved sources and showing which ones.

👀 See it in action

python
question = "How many casual leaves do new joiners get?"
chunks = vector_db.search(embed(question), top_k=4)          # retrieve
context = "\n\n".join(f"[{c.source}] {c.text}" for c in chunks)
prompt = f"Answer ONLY from the sources below. Cite them. If not found, say so.\n\n{context}\n\nQ: {question}"
answer = llm(prompt)   # → "New joiners get 8 casual leaves per year [HR-Policy-2026 §4.2]"

Retrieve → augment the prompt → generate. Plus an honest 'not found' rule.

⚠️ Common mistakes to avoid

  • Fixed size chunks that cut tables and lists in half. Respect document structure.
  • Stuffing 30 chunks into the prompt. More isn't better; a few relevant chunks usually beat many.
  • Ignoring permissions, so users see documents they shouldn't. Filter at retrieval time.

🙋 Questions learners ask

RAG or a bigger context window?

Even with huge context windows, RAG is usually cheaper, faster and more accurate, because the model sees only what's relevant. For one small document, just put it in the prompt.

How do I keep the index up to date?

Run a sync job that re-embeds changed documents and deletes removed ones, triggered by changes or on a schedule.

🎯 Asked in interviews on this topic

Try answering out loud first, then open the model answer.

Explain RAG. Why would you use it?

💬

RAG means retrieval augmented generation. It's like an open book exam for the LLM. First, we index our documents: split them into chunks, turn each chunk into an embedding and store it in a vector database. When a user asks a question, we embed the question, retrieve the most relevant chunks, put them into the prompt with an instruction like "answer only from these sources and cite them", and the LLM writes the answer. We use it because the model doesn't know our private or recent data, and RAG gives grounded answers with sources, without retraining the model.

✅

  • Two phases: indexing and answering
  • Embed, retrieve, put into prompt, generate with citations
  • Why: private and fresh data, fewer hallucinations, no retraining
  • Mention that retrieval quality decides answer quality

: The most asked LLM question of 2026. Be ready for deep follow ups.

Users say your RAG bot gives a wrong answer, even though the right document exists. How do you debug it?

💬

I'd find out where the chain broke, step by step. One: was the document indexed at all? Check ingestion logs. Two: was it retrieved? Run the query and see if the right chunk is in the top results; if not, it's a retrieval problem, like bad chunking, a filter excluding it, or the query wording differing from the document's wording. Three: was it retrieved but cut off, because of the context limit? Four: was it in the prompt, but the model ignored or misread it? That's a prompt or model problem. I'd add this case to an evaluation set and measure retrieval and generation separately, so I can fix the right part and prevent it coming back.

✅

  • Classify the failure: not indexed, not retrieved, ranked too low, truncated, or misused by the model
  • Inspect each stage with logs and traces
  • Fixes depend on stage: chunking, hybrid search, reranking, prompt changes
  • Add the case to an eval set; measure retrieval and generation separately

: Structured debugging. The step by step classification is what top answers do.

How do you choose a chunking strategy for RAG?

💬

Chunks should be big enough to hold a complete idea, but small enough to be precise. I start by respecting the document's structure: split by headings, sections or paragraphs instead of every fixed number of characters, so a table or a step list isn't cut in half. A typical starting size is a few hundred tokens with a small overlap. I attach metadata like title, section and date to each chunk, which helps filtering and citations. Then I test different sizes against an evaluation set of real questions, and keep whatever gives the best retrieval recall.

✅

  • Structure aware splitting (headings, paragraphs, tables)
  • Starting size plus overlap; tune by evals
  • Metadata on each chunk
  • Measure with retrieval recall on real questions

What are hybrid search and reranking, and why do they help?

💬

Vector search is good at meaning but can miss exact terms like product codes, names or error numbers. Keyword search, like BM25, is great at exact terms but misses paraphrases. Hybrid search runs both and merges the results, so you get the best of each. Reranking is a second step: take the top 50 or so candidates and let a more accurate, slower model, a cross encoder, score each one against the question, then keep the best 5. Together they usually give a big jump in retrieval quality for little extra effort.

✅

  • Vector = meaning; keyword = exact terms
  • Hybrid merges both result lists
  • Reranker rescores a shortlist more accurately
  • Trade off: a bit more latency for much better precision

How do you evaluate and improve a production RAG pipeline on complex PDFs and tables?

💬

I separate retrieval metrics from generation metrics. For retrieval, I track Recall@k and MRR on a golden question-to-source-chunk dataset; for generation, I measure faithfulness (zero unsupported claims) and answer relevance. Complex PDFs usually fail because naive character chunking slices tables and loses section headers. I fix that with layout-aware parsing that keeps tables intact as Markdown, prepends the document title and section breadcrumb to every chunk before embedding, combines BM25 + dense vectors with Reciprocal Rank Fusion, and uses a cross-encoder reranker to pick the top 5 chunks.

✅

  • Evaluate retrieval (Recall@k, MRR) separately from generation faithfulness
  • Layout-aware parsing that keeps Markdown tables intact and prepends section headers
  • Hybrid search (BM25 + dense embeddings) merged with Reciprocal Rank Fusion (RRF)
  • Cross-encoder reranking + query rewriting for multi-turn chats

When would you use prompting, RAG or fine tuning?

💬

I go in order of cost. First, prompting: clear instructions and examples solve many problems and take hours, not weeks. If the model needs knowledge it doesn't have, like our policies or recent data, I use RAG, because it's easy to update and gives citations. I'd fine tune when the problem is behaviour, not knowledge: a very specific output style or format, a narrow task done at huge volume where a small fine tuned model is cheaper and faster, or domain language the model handles poorly. Often the best system combines RAG with a lightly fine tuned model.

✅

  • Prompting first: fastest and cheapest
  • RAG for knowledge, especially changing or private data
  • Fine tuning for behaviour, format, cost at scale
  • They can be combined

: Judgement about cost and fit; asked for PMs too.

How do you reduce hallucinations in an LLM product?

💬

Several layers. Ground the model with RAG and tell it to answer only from the provided sources and to say "I don't know" when they don't contain the answer. Ask for citations, so users and code can check them. Lower the temperature for factual tasks. Validate outputs with code where possible, for example checking that a quoted number actually appears in the source. For high risk cases, route low confidence answers to a human. And measure the hallucination rate with an eval set, so every prompt or model change is checked.

✅

  • Grounding with retrieval and an "I don't know" rule
  • Citations and automated checks
  • Low temperature, structured output
  • Human review for risky cases; track the rate with evals

: Responsible engineering; every LLM role gets this.

In an enterprise RAG system, how do you make sure users only see documents they're allowed to see?

💬

The filtering must happen at retrieval, not in the prompt. When indexing, I store each chunk with access metadata, like the groups or users allowed to see it, copied from the source system. At query time, I get the user's identity and permissions from the login system and apply them as a filter in the vector search, so forbidden chunks never reach the model. I keep permissions in sync when they change in the source, and I test it with users of different roles. Asking the LLM to "not reveal" things is not a security control.

✅

  • Store access control metadata with each chunk
  • Filter at query time using the user's real identity
  • Keep permissions in sync with source systems
  • Never rely on the prompt for security

How would you build a chatbot that answers students' questions from college notices and PDFs?

💬

I'd use RAG. First, collect the notices and PDFs, extract their text, split it into chunks of a few paragraphs, create embeddings and store them in a vector database. When a student asks a question, embed the question, find the most similar chunks, and send them to an LLM with the instruction to answer only from them and to show which notice the answer came from. If nothing relevant is found, it should say so and point to the office. I'd test it with 30 real student questions, fix the failures, deploy it with Streamlit, and add a feedback button.

✅

  • RAG: ingest, chunk, embed, store
  • Retrieve and answer with citations
  • "I don't know" when there's no answer
  • Test set, deployment, feedback

Design a chatbot that answers employee questions from 50,000 internal documents.

💬

Clarify first: who are the users, which document types, how often they change, required latency, and who can see what. Ingestion: connectors to each source, text extraction, structure aware chunking, embeddings, and a vector store with metadata and permissions. Query: rewrite the question if it's part of a conversation, hybrid search filtered by the user's permissions, rerank, and send the top chunks to the LLM with instructions to cite and say when it doesn't know. Quality: an eval set of real employee questions, measuring retrieval recall and answer faithfulness. Operations: logging, feedback buttons, cost and latency monitoring, and incremental re indexing when documents change.

✅

  • Clarifying questions first
  • Ingestion: connectors, chunking, embeddings, metadata, permissions
  • Query: rewrite, hybrid search, permission filter, rerank, grounded generation with citations
  • Evals, feedback, monitoring, index freshness
