⚖️ AI literacy for decisions: build vs buy, cost and limits

EnglishHinglish

🏠 Real-life example

For your shop's billing, you could hire developers to build software, or subscribe to a ready app for ₹500 a month. If billing isn't what makes your shop special, you buy. The same choice comes up with AI: use an existing AI product or API, customise one, or build your own model.

💡 In simple words

Most companies should not train their own foundation models. The usual ladder is: buy an off-the-shelf AI tool → use a model API with good prompts → add RAG over your data → fine-tune → build custom models. Climb only when the step below fails. Costs include API tokens, engineering time, evals, monitoring and the human review needed for errors. Know the limits: models hallucinate, can be inconsistent, struggle with exact calculation unless given tools, and data privacy rules may restrict which providers you can use. Good AI decisions weigh value, cost, risk and time to launch.

🪜 Step by step

  1. Define the need precisely: task, volume, quality bar, latency and data sensitivity.
  2. Check what exists: a SaaS product, a model API, an open model you can host.
  3. Test the top two options on your own eval set, not on vendor demos.
  4. Compare total cost over a year: usage, infrastructure, engineers to build and maintain, and switching cost.
  5. Decide, and keep an exit path: wrap vendors behind your own interface so you can switch.

🔑 Key terms

Foundation model
A large general-purpose model (GPT, Claude, Llama) that others build on.
Total cost of ownership
All costs over time: API, people, monitoring and errors.
Vendor lock-in
Becoming dependent on one provider in a way that's hard to change.

👀 See it in action

text
Need: summarise 2,000 customer calls/day
Buy:   speech-analytics SaaS ≈ ₹2 lakh/month, live in 2 weeks
Build: transcription + LLM API ≈ ₹60k/month + 2 engineers × 3 months
Decision: buy now, revisit build if volume ×5 or custom insights are needed

A clear, numbers-based decision with a trigger for revisiting it.

⚠️ Common mistakes to avoid

  • Building custom models for problems a good API already solves well.
  • Comparing only per token price and ignoring engineering and maintenance time.

✅ Quick check

A company wants an internal Q&A bot over its policies. What's usually the right first approach?

  1. Hire a research lab
  2. Train a foundation model from scratch
  3. A model API with RAG over the policy documents
Show answer

C. A model API with RAG over the policy documents: API + RAG is cheap, fast and keeps answers current. Training from scratch is overkill.

🙋 Questions learners ask

How do I estimate LLM cost per month?

Requests per month × (input tokens × input price + output tokens × output price). Add a margin for retries and growth.

Are open source models good enough?

For many tasks, yes, especially after fine tuning. Test them on your eval set against an API model before deciding.

🎯 Asked in interviews on this topic

Try answering out loud first, then open the model answer.

When would you use prompting, RAG or fine tuning?

💬

I go in order of cost. First, prompting: clear instructions and examples solve many problems and take hours, not weeks. If the model needs knowledge it doesn't have, like our policies or recent data, I use RAG, because it's easy to update and gives citations. I'd fine tune when the problem is behaviour, not knowledge: a very specific output style or format, a narrow task done at huge volume where a small fine tuned model is cheaper and faster, or domain language the model handles poorly. Often the best system combines RAG with a lightly fine tuned model.

✅

  • Prompting first: fastest and cheapest
  • RAG for knowledge, especially changing or private data
  • Fine tuning for behaviour, format, cost at scale
  • They can be combined

: Judgement about cost and fit; asked for PMs too.

How do distributed tracing, prompt caching, semantic caching and model routing work together in an LLM gateway?

💬

Every user request gets a trace ID and child spans for query rewriting, retrieval, reranking, LLM calls and tool calls, recording exact inputs, outputs, latency, token counts and cost. In the gateway, prompt/prefix caching reuses the KV cache of static system instructions and few-shot examples across requests, cutting input token cost by 50–90%. Semantic caching embeds the query and returns a vetted cached response for high-similarity repeat FAQs (scoped by tenant and permissions). Finally, a model router sends 70–80% of simple classification or FAQ queries to a fast, cheap small model and only escalates complex reasoning to a frontier model, with automatic fallback if a provider returns 429 or 503.

✅

  • Trace + child spans capture latency, tokens, cost and prompt version at every step
  • Prompt/prefix caching reuses KV cache for static system prompts and examples
  • Semantic caching serves repeat FAQs (strictly scoped by tenant/permissions and freshness)
  • Model routing sends simple traffic to small models + automatic provider fallbacks

When should you NOT use AI to solve a problem?

💬

When a simple rule or normal software solves it reliably, like validating a PIN code format. When mistakes are very costly and can't be caught, unless a human reviews every output. When there's no data, or the data is poor. When users need exact, explainable decisions, for example some regulated decisions. And when the cost per use is higher than the value. I'd always ask: what's the simplest solution that works, and does AI's flexibility justify its error rate and cost?

✅

  • Rules work fine
  • Unacceptable or uncatchable errors
  • No or poor data
  • Explainability or regulation needs
  • Cost higher than value

: Judgement. Saying "don't use AI" in the right case is a strong signal.

How do you decide between building your own model, fine tuning, or using an API like GPT or Claude?

💬

Start with an API from a strong provider, because it's the fastest way to learn whether the feature has value. Consider building or fine tuning when there's a clear reason: costs at our volume are too high and a smaller tuned model could match quality; data can't leave our environment; latency needs are strict; or the task is very specialised and we have good data. I'd compare total cost, including the engineers to maintain it, quality on our own eval set, privacy, and vendor lock in, and design the system so the model can be swapped.

✅

  • API first to validate value
  • Reasons to build: cost at scale, privacy, latency, specialisation
  • Compare total cost and quality on your evals
  • Keep the model swappable

: Business and technical trade off thinking.

How do you evaluate unit economics and UX trade-offs when launching a multimodal (vision or voice) AI feature?

💬

High-resolution images, multi-page PDFs and live audio consume far more tokens and bandwidth than plain text, and a single user retry or multi-step loop can multiply cost 3× to 5×. I calculate cost per successfully completed task—not just cost per API call—and compare it against the user's willingness to pay or the operational cost saved. To keep margins healthy, I resize images before sending, route simple extractions to a small vision model, cache repeated documents, and design the UI with instant visual/audio feedback and a clear human fallback when confidence is low.

✅

  • Measure cost per completed task (including retries), not just cost per API call
  • High-res images and live voice have much higher token/compute cost than text
  • Use image resizing, model routing and caching to protect gross margin
  • Design UX for latency (streaming/barge-in) and verification on extracted fields

Buy → API → RAG → fine-tune → build. Climb only when needed.
