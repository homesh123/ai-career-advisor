🤝 Building with AI coding assistants: spec, review, test

EnglishHinglish

🏠 Real-life example

A very fast junior developer joins your team. They type ten times faster than you, never get tired, and sometimes confidently do the wrong thing. You'd give them a clear task, small pieces at a time, review every change and make them run the tests. Tools like Claude Code, Cursor and GitHub Copilot are that junior: hugely useful if you lead them well.

💡 In simple words

Many AI product teams now expect engineers to build with AI coding assistants every day. They come in three forms: inline completion in the editor, chat in the editor that edits files, and agents that run in the terminal or the cloud, read the codebase, run commands and tests, and open pull requests. Used well, they speed up boilerplate, tests, refactors and learning a new codebase. Used badly, they add code nobody understands. A good workflow: write a short spec first (goal, files, constraints, what done looks like); give the tool project context through a file such as CLAUDE.md or a rules file (stack, commands, conventions); work in small steps; make it write or update tests and run them; read every diff as if a colleague wrote it; and commit often so you can roll back. Never paste secrets or private customer data into a tool your company hasn't approved. In interviews, many companies now allow AI tools in coding rounds and judge how you direct, check and explain the result, so practise thinking out loud while you use them.

🎬 See how it works

You lead, the assistant types: write a spec, give project context, let it plan and code in small steps, run the tests, then review the diff before you commit.

🪜 Step by step

  1. Pick the tool your team uses (Claude Code, Cursor, Copilot or similar) and learn its three modes: completion, editor chat and agent.
  2. Write a project context file with the stack, commands, folder layout and rules, and keep it short and current.
  3. Before each task, write a 5 line spec: goal, files involved, constraints, tests, and what done looks like.
  4. Ask for a plan first, then implement in small steps, running tests after each step.
  5. Review every diff: does it match the spec and conventions, handle errors, avoid new dependencies you didn't want, and keep secrets out?
  6. Commit in small pieces with clear messages so you can roll back a bad step.

🔑 Key terms

Coding agent
An assistant that reads the codebase, edits files, runs commands and tests, and proposes changes.
Project context file
A file such as CLAUDE.md or a rules file that tells the tool your stack, commands and conventions.
Spec first
Writing the goal, constraints and "done" before asking the tool to code.
Diff review
Reading every change line by line before accepting it.

👀 See it in action

markdown
# CLAUDE.md (project context for the coding assistant)
Stack: Next.js 15, TypeScript, Vercel AI SDK, Postgres + pgvector, Zod.
Commands: `npm run dev` · `npm test` · `npm run evals` · `npm run lint`
Rules:
- All model calls go through lib/ai.ts (logs cost and latency).
- Never expose keys to the client; no NEXT_PUBLIC_ secrets.
- Every new route: auth + rate limit + Zod validation.
- Write or update tests for every change and run them before finishing.

# Task spec I give the assistant
Goal: add a "Summarise ticket" button on /tickets/[id].
Done when: streams into a side panel, Stop works, 3 unit tests pass,
           eval set for summaries stays ≥ 0.85.

Context file plus a clear spec plus tests turns a fast assistant into a reliable teammate.

⚠️ Common mistakes to avoid

  • Accepting a huge change you don't understand because the demo works.
  • Pasting API keys, customer data or private code into a tool your company hasn't approved.
  • Vague prompts like "make it better", which produce random changes across many files.

✅ Quick check

An AI coding agent produced a 400 line change that passes the tests. What should you do before merging?

  1. Merge it, the tests pass
  2. Read the diff carefully, check it matches the spec and conventions, and ask for smaller steps if it's hard to review
  3. Ask the agent whether the code is good

B. Read the diff carefully, check it matches the spec and conventions, and ask for smaller steps if it's hard to review: Passing tests only shows what the tests check. You own the code you merge, so you must understand it, and smaller changes are easier to review well.

🙋 Questions learners ask

Will AI coding tools replace AI product engineers?

They change the job more than remove it: less typing, more specifying, reviewing, testing and product judgement. Engineers who direct these tools well ship much faster.

Can I use AI tools in interviews?

Only if the company says so; many now allow them in some rounds. Ask at the start, and if allowed, explain your plan, check the output aloud and fix issues yourself.

How do you use AI coding assistants in your day to day work, and how do you make sure the code is good?

For example, I used this to add streaming summaries to our ticket page in two days, with tests, instead of a week.
