🏪 Feature stores and data labeling: offline vs online data and avoiding skew

EnglishHinglish

🏠 Real-life example

Suppose a student practises for a maths exam using a calculator where 'log' means base 10, but in the exam hall the calculator's 'log' button means natural log (base e). Even a well-prepared student will get every answer wrong! That's training-serving skew: when a feature like 'user_7d_spend' is calculated one way in SQL during training and a slightly different way in production code. A feature store defines the recipe once and serves both.

💡 In simple words

Production ML models need two kinds of access to the exact same features. Training needs millions of historical rows with 'point-in-time' accuracy (what did we know about this user at the exact minute of the transaction, with zero future leakage?). Live inference needs the latest feature values for one user in under 10 milliseconds. A feature store (like Feast or Tecton) solves both: it writes features from one shared definition to an offline store (warehouse/Parquet for training) and an online store (Redis/DynamoDB for low-latency serving). Alongside features, high-quality labels come from clear labeling guidelines, measuring inter-annotator agreement, and active learning (sending the model's most uncertain cases to human reviewers).

🎬 See how it works

One feature definition writes historical values to the offline warehouse for point-in-time training and the latest values to the online store for millisecond live inference.

🪜 Step by step

  1. Define each feature transformation once in version-controlled code (SQL or Python/Spark) with a clear owner and entity key (e.g. user_id).
  2. Materialise historical feature values into the offline store (Snowflake, BigQuery, Parquet) with accurate event timestamps.
  3. Build training datasets using point-in-time (ASOF) joins so each training label only sees feature values that existed before that label's timestamp.
  4. Sync the latest feature values to an online low-latency key-value store (Redis, DynamoDB) for real-time model serving.
  5. For labeling, write a 1-page rubric with edge-case examples, check agreement across two annotators on a 5% sample, and use active learning to label hard failures first.

🔑 Key terms

Offline vs online store
Offline store holds historical tables for training; online store (e.g. Redis) serves the latest row per entity in milliseconds.
Point-in-time join (ASOF join)
Joining each training label with feature values as they existed at that exact timestamp, preventing future data leakage.
Active learning
Picking the unlabelled examples where the model is most uncertain (or disagrees) for humans to label first.

⚠️ Common mistakes to avoid

  • Rewriting a Python/Pandas feature in Java or Go by hand for production without testing that both produce identical numbers on 1,000 real inputs.
  • Having 5 annotators label 10,000 rows with vague instructions and never measuring inter-annotator agreement, resulting in noisy labels that cap model accuracy.

✅ Quick check

When building a training dataset for fraud detection, why must you use a point-in-time join instead of joining on today's latest user table?

  1. SQL does not support timestamps
  2. Point-in-time joins use fewer columns
  3. Joining today's table leaks future information (like account blocks that happened after the fraud) into past training rows
Show answer

C. Joining today's table leaks future information (like account blocks that happened after the fraud) into past training rows: Using feature values from after the event timestamp is time-travel data leakage: offline AUC looks 0.99, then production fails.

🙋 Questions learners ask

Does every team need a full feature store like Feast or Tecton?

No! If your models run in nightly batch, well-tested dbt tables are enough. You need an online feature store when real-time models need fresh historical aggregates in milliseconds.

How do you handle streaming features like 'clicks in the last 5 minutes'?

A stream processor (Kafka + Flink/Spark Streaming) updates a sliding-window counter in the online store and logs events to the offline store so training and serving stay aligned.

🎯 Asked in interviews on this topic

Try answering out loud first, then open the model answer.

What is training serving skew, and how do you prevent it?

💬

It's when the data the model sees in production is computed differently from the data it was trained on, so the model quietly performs worse. For example, in training "average spend" was computed over 30 days in SQL, but the live service computes it over 7 days in Python. Prevention: use one shared feature pipeline or a feature store for both training and serving, log the features used at prediction time and compare them with training data, and add tests that run the same input through both paths.

✅

  • Definition and a concrete example
  • Cause: two different code paths for features
  • Fix: shared pipeline or feature store, logging, comparison tests

: Production ML maturity.

How does a feature store work, and what is a point-in-time (ASOF) join?

💬

A feature store defines a feature once and materialises it to two storage layers: an offline store (Parquet/Delta/warehouse) for large historical training sets, and an online key-value store (like Redis or DynamoDB) for single-digit-millisecond lookups during live inference. When building historical training data, a regular join on user_id leaks the future because it pulls today's feature values for an event that happened six months ago. A point-in-time or ASOF join matches each historical label at timestamp T with the latest feature value recorded at or before T, guaranteeing zero time-travel leakage.

✅

  • One feature definition → offline store (training batches) + online KV store (low-latency serving)
  • Eliminates training–serving skew across SQL and Python paths
  • Point-in-time (ASOF) join matches each label at T with features from <= T
  • For labeling: combine weak/LLM pre-labels with human verification and inter-annotator agreement

: High-signal question for AI Data Engineers, ML Engineers and MLOps Engineers.

Design a real time fraud detection system with a 150 ms latency budget.

💬

Clarify the cost of missed fraud versus false declines, and the review team's capacity. Features: real time features like the number of transactions from this card in the last 10 minutes, computed from a stream, plus historical features from a feature store; accept that some features are slightly stale to meet latency. Model: gradient boosting, fast and strong on tabular data, with a threshold chosen for the business trade off, and a middle band sent to manual review. Serving: a low latency service with features cached in memory or Redis, and a fallback rule if the model is slow. Labels arrive late through chargebacks, so monitor drift and retrain regularly, and keep rules for brand new fraud patterns.

✅

  • Clarify costs of each error type
  • Streaming plus stored features; staleness trade off
  • Fast model, threshold with review band
  • Low latency serving with fallback; delayed labels, drift, retraining

: Latency, features and business trade offs together.

Design the data pipeline that feeds daily sales analytics and an ML demand forecast.

💬

Sources: order database via change data capture, product catalogue, and store data. Land raw data in a lake or warehouse partitioned by date. Transform with dbt into clean staging tables, then a star schema with an orders fact table and product, store and date dimensions. The ML team reads a feature table built from the same models, so analytics and ML agree. Orchestrate with Airflow, each task idempotent by date, with data quality tests between layers, and alerts if data is late or wrong. Backfills are reruns of date partitions. Document lineage and owners, so people know where numbers come from.

✅

  • Sources and ingestion (CDC)
  • Raw → staging → modelled layers (star schema)
  • Shared feature tables for ML
  • Orchestration, idempotency, quality tests, backfills, lineage

: End to end data architecture.

📌 Remember

Define features once, join training data point-in-time, serve live features from an online store, and focus labeling on hard cases.
